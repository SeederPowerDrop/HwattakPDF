# HwattakPDF 목표 적합성 및 버그 점검 — 2026-09-05

> 후속: 아래는 수정 전 점검 기록이다. 확인한 문제의 수정과 이후 검증은 [2026-09-05 안정화 기록](STABILIZATION-2026-09-05.md), [2026-09-09 추가 버그 수정](STABILIZATION-2026-09-09.md)을 참고한다.

## 판정

**제품 방향은 목표와 잘 맞는다. 다만 현재 개발 트리를 다음 공개 릴리스로 내기 전에 저장 수명과 변환 입력의 일관성을 보완해야 한다.**

개발노트의 출발점은 구독 없이 내 Mac에서 오래 쓸 수 있는 PDF 도구였고, 제품 정의는 로컬 처리·파일 소유권·데이터 손실 방지·대용량 읽기·학습을 우선한다. 현재 탭·스택·비교·페이지 조립·주석·서명·검색·로컬 OCR은 이 목표에 맞는 구성이다. 저장 충돌 검사, 문서별 델타 Undo, clean 탭 휴면, AI 요청별 승인도 구체적인 코드와 테스트를 갖췄다.

반면 기존 본문·이미지 객체의 직접 편집은 아직 없고, 자동 복구 저널과 실문서 장시간 성능 검증도 남아 있다. 따라서 읽기·공부·페이지 조립 작업 공간으로는 설득력이 있지만, 모든 전문 PDF 편집 작업을 대체하는 완성품이라는 평가는 이르다. 새 변환 기능의 확장보다 안정화 마일스톤을 먼저 닫는 것이 현재 목표에 더 잘 맞는다.

## 확인한 문제

### 1. [P1] 이미지 편집 결과를 임시 폴더에 저장하고 저장 완료로 표시

**재현:** PNG를 일반 열기로 열고 에디팅 모드에서 회전한 뒤 저장의 ‘원본 덮어쓰기’ 경로를 선택한다.

**실제 결과:** `outcome=saved`, `dirty=false`. 저장 위치는 `…/T/HwattakPDF-ImagePreviews/<UUID>/image-save.png.pdf`이고 원본 PNG bytes는 바뀌지 않았다. 사용자가 다시 원본 PNG를 열면 저장한 편집이 보이지 않으며, 유일한 편집 사본은 OS 임시 파일 정리에 취약하다.

**원인:** `ImagePDFConverter.makePreviewPDF`가 만든 임시 URL을 일반 PDF의 `documentURL`로 설치한다. 저장 UI는 `documentURL != nil`만으로 ‘원본 덮어쓰기’를 제공하고, 저장 모델은 임시 문서 여부를 구분하지 않은 채 clean으로 바꾼다. 원본 이미지 이름만 표시하므로 저장 대상에 대한 오해도 생긴다.

- 위치: `Sources/VibePDF/Services/ImagePDFConverter.swift:65`, `Sources/VibePDF/Models/MultiDocumentWorkspaceState.swift:785`, `Sources/VibePDF/App/UnsavedChangesGuard.swift:133`, `Sources/VibePDF/Models/PDFWorkspaceState.swift:987`.
- 권장 수정: 원본 이미지 URL, 임시 렌더 backing URL, 영구 저장 URL을 모델에서 구분한다. 이미지에서 파생된 미저장 PDF의 첫 저장은 반드시 사용자 지정 PDF 저장 위치를 받으며, 성공한 영구 저장에만 dirty를 해제한다. 세션 복원과 캐시 정리도 같은 문서 수명 규칙을 따른다.
- 완료 기준: 이미지 편집 후 저장·닫기·재실행·원본 다시 열기를 검사하고, 임시 파일 삭제 후에도 사용자가 저장한 결과가 보존되는지 확인한다.

### 2. [P2] PDF 만들기에서 선택 이후 변경된 원본을 알림 없이 사용

**재현:** 원본 PDF의 페이지를 조립 목록에 추가하고, 저장 전에 다른 작성자로 원본 페이지를 90도 회전해 저장한 다음 조립을 실행한다.

**실제 결과:** 선택 당시 회전은 0도였지만 조립 결과는 90도였다. 오류는 없고 `lastSavedURL`도 성공으로 설정됐다. 페이지 삽입·삭제로 인덱스가 바뀌면 선택 당시와 다른 페이지를 가져올 수 있는 같은 구조다. 이번 동적 재현은 회전 변경으로 확인했다.

**원인:** 선택 모델은 URL·페이지 수·권한만 보관하고, 조립 항목은 URL과 페이지 인덱스만 저장한다. export 시 파일을 다시 열면서 선택 시점의 파일 버전이나 페이지 snapshot을 검사하지 않는다. 기존 일반 PDF 저장에는 있는 외부 변경 경계가 새 가져오기 경로에는 없다.

- 위치: `Sources/VibePDF/Models/ImagePDFAssemblyModel.swift:65`, `:130`, `:384`.
- 권장 수정: 선택 시 파일 버전을 기록하고 export에서 일치 여부를 확인하거나, 선택 페이지의 불변 snapshot을 보존한다. 변경을 감지하면 사용자에게 재선택을 안내한다. 파일이 여러 항목에 사용되는 경우도 같은 버전이어야 한다.
- 완료 기준: 선택 이후 회전·내용 교체·페이지 삽입·삭제된 원본을 조립해, 알림 없이 다른 결과가 나오는 경로를 막는다.

### 3. [P2] 같은 이미지를 다시 열면 기존 탭 대신 중복 탭 생성

**재현:** 동일한 PNG URL을 일반 열기 경로로 두 번 연다.

**실제 결과:** 탭 수가 2개가 되고 activeTabID도 달라졌다. 각 탭의 파일은 별도 UUID 아래에 생성된 서로 다른 임시 PDF다.

**원인:** 기존 PDF 중복 검사에 도달하기 전에 매번 새로운 임시 PDF를 생성하므로, 같은 이미지라는 원본 식별 정보가 사라진다. 두 탭의 독립 편집과 1번 저장 문제를 함께 만나면 어느 결과를 저장했는지 혼란이 커진다.

- 위치: `Sources/VibePDF/Models/MultiDocumentWorkspaceState.swift:778`, `Sources/VibePDF/Services/ImagePDFConverter.swift:68`.
- 권장 수정: 이미지 변환 전에 원본 파일 identity로 열린 탭을 조회한다. 원본 identity와 임시 렌더 파일 identity를 분리하는 1번 수정과 함께 처리하는 편이 좋다.
- 완료 기준: 동일 이미지 반복 열기와 한 배치의 중복 입력이 기존 탭을 선택하고, 다른 폴더의 동명 이미지는 독립 탭으로 열린다.

## 재현 버그와 구분해야 할 기존 한계 및 추가 위험

- 자동 저장/복구 저널, 기존 본문 및 이미지 객체 편집, secure redaction, 인증서 서명은 미구현이다. 이미 문서화된 범위이므로 새 버그로 집계하지 않았다.
- OCR 체크포인트는 평문이며 자동 만료/앱 내 삭제 UI가 없다. 로컬 우선 원칙에 더해 사용자가 로컬 잔존 데이터를 관리할 수 있어야 한다.
- 일반 PDF 저장의 파일 단위 권한 fallback은 사전·사후 검증을 하지만 직접 쓰기 중 프로세스 종료까지 원자적으로 보호하지 않는다. 제품 품질 목표의 ‘저장 중 종료에도 원본 무손상’은 아직 전체 경로에서 충족하지 못한다.
- 새 이미지 일괄 열기는 MainActor에서 이미지를 동기 변환한다. Office 내보내기도 MainActor 호출에서 전체 페이지를 순회하고 모든 PNG와 최종 ZIP을 메모리에 모은다. 페이지당 픽셀 상한이 전체 작업의 메모리 상한은 아니다. 대용량에서 응답 중단/메모리 증가가 예상되는 코드 구조이지만, 이번 점검에서는 장시간 성능 수치를 측정하지 않았으므로 실측 버그로 보고하지 않는다.
- HTML의 원격 자원 차단과 같은 폴더 자원 로딩은 실제 배포 sandbox·네트워크 관찰로 확인해야 한다. unrestricted XCTest 통과는 배포 앱의 파일 접근 권한 검증과 같지 않다.
- `PDFWorkspaceState` 3,731줄, `MultiDocumentWorkspaceState` 1,826줄, `PDFKitViewer` 1,816줄에 책임이 집중돼 있다. 줄 수 자체를 버그로 보지는 않지만, 새 변환 경로가 기존 저장 수명 규칙을 공유하도록 책임 분리가 필요하다. 언어/프레임워크 전면 교체를 뒷받침하는 성능 근거는 이번 감사에 없다.

## 권장 개발 순서

1. 이미지 파생 문서의 영구 저장·세션 복원·중복 방지를 함께 수정하고 원본 변경 감지를 변환 입력까지 확장한다.
2. 복구 저널과 OCR 체크포인트 정리 UI를 구현해 저장/개인정보 관리의 빈틈을 줄인다.
3. 대용량 실제 자료, 배포 sandbox/File Provider, Word·PowerPoint와 외부 PDF 뷰어의 호환성을 검증한다. 새 변환 작업에는 취소·진행률·작업 전체 리소스 예산을 적용한다.
4. 읽기/학습 흐름의 주석 목록·책갈피·노트 회수를 완성한 뒤, 실제 본문 편집 엔진이나 더 넓은 서비스 연동의 범위를 결정한다.
