# HwattakPDF 안정성 재검토 — 2026-09-08~09

> 후속: 아래는 수정 전 감사 기록이다. 확인한 6개 결함의 수정과 검증은 [2026-09-09 안정화 기록](STABILIZATION-2026-09-09.md)에 정리했다.

## 판정과 범위

**기존 정상 경로의 회귀 검사는 통과했지만, 추가 검사에서 종료·권한·복구 문제를 재현했다. 현재 개발 트리를 안정화 완료 또는 공개 배포 준비 완료로 판정하지 않는다.**

기준은 Git HEAD `1584312`와 검토 시작 시점의 미커밋 변경 전체다. 공개 0.8.0 ZIP이 아니라 9월 5일 안정화 및 플러그인 확장이 포함된 개발 트리를 검사했다. 검토는 9월 8일에 시작해 9일에 마쳤다. 제품 코드는 수정하지 않았고, 아래 항목은 아직 해결되지 않은 발견이다.

저장·복구·세션 복원, 문서 수명, 검색·OCR·대용량 로딩, 이미지/HTML/Office 변환, 플러그인 권한, 압력 필기와 페이지 추출을 확인했다. 사용자의 실제 PDF에는 쓰지 않았으며 합성 자료와 격리된 저장소를 사용했다.

## 확인한 문제

### 1. [P1] 압력 필기가 있는 페이지를 추출하면 프로세스 종료

- 재현: 일반 PDF 페이지에 `PressureInkAnnotation`을 추가한 뒤, 원본을 저장·재개방하지 않은 상태에서 `PDFPageOperations.extract`로 추출하고 결과를 PDF로 직렬화한다.
- 결과: 다른 테스트와 함께 실행할 때와 단독 새 프로세스에서 모두 `SIGSEGV`(signal 11)로 종료했다. 페이지 복사는 성공하고 독립 주석 1개까지 확인되지만, 결과의 `dataRepresentation()`이 복제된 `PressureInkAnnotation.draw()`를 호출하면서 `points.count`에서 `EXC_BAD_ACCESS(0x10)`이 발생한다. 디버거 호출 스택도 확보했다. 기존의 필기 저장→재개방 및 Undo 검사는 이 경로를 검사하지 않았다.
- 영향: 필기를 포함한 선택 페이지 내보내기에서 앱 전체가 종료될 수 있어 다른 탭의 미저장 작업에도 영향을 줄 수 있다. 이번 재현은 제품의 실제 추출 서비스를 호출한 XCTest이며 설치 앱의 GUI 클릭 재현은 별도로 하지 않았다.
- 위치: `Sources/VibePDF/Services/PDFPageOperations.swift:24`, `Sources/VibePDF/Models/PressureInkAnnotation.swift:43`. 사용자 선택 페이지 내보내기는 `Sources/VibePDF/Models/PDFWorkspaceState.swift:1435`에서 같은 추출 서비스를 사용한다.
- 수정 방향: 사용자 정의 필기 주석의 복제·직렬화 계약을 보완하거나, 해당 주석이 포함된 페이지를 검증된 PDF 직렬화 경로로 분리한다. 배열·색상·외형이 독립 복사본에 보존되는지 확인해야 한다. `init(coder:)`가 nil을 반환하는 것만으로 원인을 단정하지 않는다.
- 완료 기준: 첫 저장 전/후의 필기 페이지를 합본 추출·개별 추출하고 결과를 재개방·렌더링한다. 원본의 Undo/Redo와 추출 문서의 독립성도 함께 검사한다.
- 증거: `work/audit-2026-09-08/plugin-pressure-reproduction.log`, `plugin-pressure-backtrace-full.log`, `reproductions/AuditPluginStabilityTests.swift`.

### 2. [P1] 비정상 페이지 크기를 가진 PDF의 Office 내보내기가 종료

- 재현: 페이지 크기가 `1e20 × 1e20` 포인트인 작은 합성 PDF를 디스크에 저장하고 다시 연 뒤 Word로 내보낸다. `workspace.open`은 성공하고 `canRasterizePages`도 true다.
- 결과: 실제 `exportResponsive`가 래스터 작업의 진행률 `0.85`까지 진행한 뒤 `SIGTRAP`(signal 5)으로 종료했다. 페이지 픽셀 수는 제한하지만 Open XML의 용지 크기에는 원본 크기를 그대로 사용한다.
- 원인: `Int(canvas.width * 20)`처럼 범위를 검증하지 않은 정수 변환이 있다. `max(1, …)`는 `Int` 변환 이후에 적용되므로 변환 trap을 막지 못한다. PowerPoint의 `* 12_700` 경로에도 같은 구조가 있으나 이번 동적 재현은 Word다.
- 위치: `Sources/VibePDF/Services/PDFOfficeExporter.swift:173`, `:180`, `:212`.
- 수정 방향: PDF 크기를 읽는 시점에 유한성·양수·변환 가능한 범위 및 Office 용지 범위를 검사하고, 지원하지 않는 크기는 오류로 반환하거나 명시된 출력 크기로 정규화한다.
- 완료 기준: 정상·회전·혼합 크기 문서와 비정상 크기 문서를 Word/PowerPoint 모두에 보내 종료 없이 정상 결과 또는 오류를 받고, 실패 시 기존 목적지 파일을 보존한다.
- 증거: `work/audit-2026-09-08/conversions/office-extreme-3.log`, 같은 폴더의 합성 fixture, `reproductions/AuditConversionStabilityTests.swift`.

### 3. [P1] 선택 텍스트 플러그인이 PDF의 복사 금지 권한을 건너뜀

- 재현: 복사 권한을 금지한 암호 PDF를 사용자 암호로 연다. `permissionsStatus == .user`, `allowsCopying == false`, `workspace.allows(.copyAndPaste) == false`를 확인한 뒤 선택 텍스트를 사용하는 유효한 `copyText` 플러그인을 실행한다.
- 결과: 명령이 사용 가능으로 판정되고 오류 없이 실행되어 합성 문구 `CONFIDENTIAL`이 클립보드 쓰기 콜백에 전달됐다. 실제 시스템 클립보드 대신 테스트용 콜백을 사용했다.
- 원인: 플러그인 자체의 `selectedText`·`clipboardWrite` 권한은 검사하지만 `snapshotContext`가 현재 PDF의 복사 권한을 확인하지 않고 `PDFSelection`에서 텍스트를 추출한다. 플러그인 설치 동의와 문서의 허용 작업은 별개의 검사다.
- 위치: `Sources/VibePDF/Plugins/PluginActionRunner.swift:630`.
- 수정 방향: 선택/페이지 텍스트를 추출하기 전에 문서의 복사 정책과 선택의 현재 문서 소속을 확인한다. 명령 활성화와 실제 실행이 같은 정책을 사용해야 한다.
- 완료 기준: 복사 허용/금지, 사용자/소유자 암호, `showText`/`copyText`/`openURL` 조합을 검사한다. 권한이 없는 경우 텍스트가 출력·클립보드·URL 승인 콜백까지 전달되지 않아야 한다.
- 증거: `work/audit-2026-09-08/plugin-restricted-reproduction.log`, `reproductions/AuditPluginStabilityTests.swift`.

### 4. [P2] 편집 직후 OCR을 실행하면 자동 복구본이 생성되지 않을 수 있음

- 재현: 자동 복구를 켠 1페이지 문서를 회전하고, 복구의 5초 대기 시간이 끝나기 전에 6초 동안 실행되는 OCR 작업을 시작한다. OCR 완료 후에도 5.5초 더 기다린다.
- 결과: 문서는 dirty이고 OCR은 정상 완료했지만 복구 기록은 0개였다. 복구 경고도 없었다. OCR 시간은 주입 가능한 기존 테스트 경계를 이용해 고정했으며 Vision 정확도를 검사한 것은 아니다.
- 원인: 복구 예약이 OCR 실행 중이면 재예약 없이 반환한다. OCR의 성공·취소·실패 종료부에도 복구 재예약이 없다. 따라서 추가 편집이나 별도 저장이 없으면 해당 변경의 복구 사본이 계속 없는 상태다.
- 위치: `Sources/VibePDF/Models/PDFWorkspaceState.swift:215`, `:3525`.
- 수정 방향: OCR 종료 시 dirty 상태의 복구를 다시 예약하거나, 건너뛴 예약을 지연 처리한다. 문서 교체·취소·비활성화와 섞여도 이전 문서를 저장하지 않도록 문서 identity를 함께 확인한다.
- 완료 기준: OCR 성공·취소·실패가 복구 대기 시간을 넘기는 각 상황에서 마지막 편집이 복구되며, 복구 기능을 끈 경우에는 저장하지 않는다.
- 증거: `work/audit-2026-09-08/recovery-scheduling.log`, `reproductions/AuditRecoverySchedulingTests.swift`.

### 5. [P2] 재실행 후 비활성 복구 탭이 ‘다른 탭 닫기’에 남음

- 재현: 복구 탭과 일반 탭을 세션에 기록하고, 일반 탭이 활성화된 상태로 복원한다. 비활성 복구 탭을 닫기 대상으로 전달한다.
- 결과: 저장/폐기 확인 호출은 0회(기대 1회)이고 실제 `closeTab`은 false였다. 원본 PDF 손실은 확인하지 않았다.
- 원인: 복구 탭은 `document == nil`, `isDirty == true`인 휴면 상태로 복원된다. 닫기 가드는 `document != nil`인 탭만 처리하여 성공을 반환하지만, 실제 닫기 모델은 dirty 상태를 이유로 거부한다.
- 위치: `Sources/VibePDF/App/UnsavedChangesGuard.swift:261`, `Sources/VibePDF/Models/WorkspaceSessionStore.swift:486`, `Sources/VibePDF/Models/MultiDocumentWorkspaceState.swift:1362`.
- 수정 방향: 휴면 중인 열린 문서도 닫기 대상으로 취급하고, 저장을 선택하면 먼저 재개한다. 폐기를 선택하면 복구 작업 사본을 포함한 수명 정리가 실행돼야 한다.
- 완료 기준: 다른 탭/스택/창/앱 닫기에서 저장·폐기·취소가 일관되게 동작한다.
- 증거: `work/audit-2026-09-08/recovery-lifecycle.log`, `reproductions/RecoveryLifecycleAuditTests.swift`.

### 6. [P2] 읽기 전용 PDF의 지우개가 실패한 삭제를 성공으로 기록

- 재현: 주석 변경 권한이 없는 PDF를 사용자 암호로 열고 에디팅 모드에서 지우개로 기존 주석을 지운다.
- 결과: PDFKit은 실제 삭제를 거부해 주석이 남았지만 모델은 true를 반환하고 dirty 상태와 삭제 메시지를 기록했다. 이 입력에서 실제 원본 주석이 삭제됐다고 보고하지 않는다.
- 원인: 지우개 경계가 도구·모드·문서 소속을 확인하면서도 `allows(.markup)`를 빠뜨리고, `removeAnnotation` 이후 실제 삭제 여부도 확인하지 않는다.
- 위치: `Sources/VibePDF/Models/PDFAnnotationErasePolicy.swift:125`, `:133`.
- 수정 방향: 주석 쓰기 권한을 변경 전에 검사하고, 실제 적용된 변경만 Undo와 dirty 상태에 반영한다.
- 완료 기준: 읽기 전용 문서에서 삭제·변경 기록·저장 요구가 발생하지 않고, 편집 가능한 문서의 정상 지우기와 Undo는 유지된다.
- 증거: `work/audit-2026-09-08/plugin-restricted-reproduction.log`.

## 재현 버그로 집계하지 않은 사항

- 다른 문서의 선택 객체를 모델에 직접 주입하면 플러그인으로 그 텍스트가 전달된다. 방어 부족은 확인했지만 실제 UI에서 그 상태가 만들어지는 경로를 확인하지 못해 별도 사용자 버그로 집계하지 않았다.
- 휴면 이미지 탭의 종료 정리 생략, 복구 작업 사본/고아 파일의 보존량, 큰 문서 복구 직렬화의 메인 스레드 지연은 후속 확인이 필요하다. 이번에 장시간 디스크·메모리 압박을 실측하지 않았다.
- 실제 iPad/Sidecar/Wacom 입력, macOS 14·26, File Provider/iCloud 및 파일 단위 sandbox 저장 권한, 실제 Word·PowerPoint의 다양한 문서, 수십~수백 개 대형 실문서 장시간 스크롤은 이번 검사 범위 밖이다.

우선 두 종료 경로와 PDF 권한 누락을 수정하고, 복구 예약·닫기·지우개의 상태 불일치를 같은 안정화 단계에서 처리한다. 그 후 추가 재현을 정규 회귀로 편입하고 실제 배포 앱과 기기 검증을 진행하는 순서가 적절하다.
