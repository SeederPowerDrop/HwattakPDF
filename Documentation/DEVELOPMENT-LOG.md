## 시작: 구독에 화가 나서 직접 만들기로 했다

유료로 구입해 사용하던 PDF 프로그램의 기본 기능까지 구독으로 바뀌었다. 회사도 먹고살아야 한다는 사정은 이해하지만, 기존 유료 구매자에게는 너무한 변화처럼 느껴졌다. 그래서 화딱지가 난 김에 “내가 자주 쓰는 기능은 내 Mac에서 오래 쓸 수 있는 앱으로 만들어 보자”고 시작한 것이 HwattakPDF다.

처음부터 거대한 PDF 엔진을 새로 쓰겠다는 계획은 아니었다. macOS의 PDFKit, SwiftUI, AppKit, Vision을 조합해 먼저 실제로 쓸 수 있는 도구를 만들고, 사용하면서 불편한 점을 한 가지씩 고치는 바이브 코딩 방식이었다. 다만 기능이 늘어날수록 “그럴듯하게 보이는 데모”보다 저장 안전성, 메모리 수명, 테스트와 정직한 한계 설명이 더 중요해졌다.

가능한 한 오래 무료로 지원하고, 만족한 사람이 자발적으로 작은 tip을 보낼 수 있는 프로젝트로 남기는 것이 제작자의 방향이다. 이 약속과 실제 오픈소스 라이선스 조건은 별도이므로 당시에는 공개 전 라이선스 결정이 남아 있었고, 0.8.0 공개 준비에서 MPL-2.0으로 확정했다.

## 1막: PDF를 편하게 읽는 화면

첫 중심은 읽기였다. 한 페이지를 크게 보는 것만으로는 교재와 논문을 훑기 불편해서 다음 흐름을 만들었다.

- PDFKit 기반 1페이지와 책처럼 펼친 2페이지 보기
- 한 번에 여러 페이지를 훑는 지연 렌더링 개요
- 1·2·4페이지 빠른 전환과 최대 12열 직접 입력
- 현재 페이지 번호 입력 이동과 스크롤 HUD
- 페이지 썸네일 패널을 좌·우·상·하에 놓고 구분선을 드래그해 크기 조절
- `⌥+스크롤` 확대, `⇧+세로 휠` 가로 이동, 기존 핀치와 일반 스크롤 유지

이 과정에서 “4페이지를 보여 준다”와 “4페이지에서 정밀 편집한다”는 다른 문제라는 경계도 생겼다. 3~12열은 빠르게 구조를 보고 페이지를 고르는 개요이고, 정밀 선택과 주석은 PDFKit 1·2페이지 보기에서 맡는다.

## 2막: 브라우저처럼 많은 PDF를 다루기

여러 자료를 동시에 보는 사용자는 브라우저 탭을 수십 개 열듯 PDF도 많이 연다. 단순 탭에서 시작해 실제 사용 피드백을 따라 구조가 커졌다.

- 탭 좌우 재정렬과 같은 파일 중복 열기 방지
- 탭 중앙에 드롭하면 Vivaldi처럼 쌓이는 2단 탭 스택
- 스택 접기·이름 변경·멤버 관리
- 스택의 탭을 상단으로 꺼내거나 별도 HwattakPDF 창으로 분리하는 tear-out
- 작업 주제별 workspace 생성·전환과 탭 이동
- 2~4개 문서를 좌우·위아래로 나누고 비율 기반 스크롤 동기화
- 분할 경계 드래그로 패널 순서와 너비·높이 조절

드래그 앤 드롭은 “드롭되기만 하면 된다”가 아니었다. 재정렬하려는지, 스택을 만들려는지, 창 밖으로 떼려는지 사용자가 눈으로 예측할 수 있어야 했다. 매끄러운 hover 의도, 안전한 취소, 기존 탭 상태를 잃지 않는 세션 이동이 중요한 완성도 기준이 되었다.

## 3막: 페이지 조립과 주석을 실제 작업으로 만들기

읽기 앱에서 작업 공간으로 넘어가며 페이지 재정렬·회전·삭제·추출·병합을 추가했다. Finder에서 PDF를 탭 막대에 놓으면 새 탭으로 열고, 문서 위에 놓으면 선택 페이지 뒤에 병합하는 문맥도 나눴다.

펜, 하이라이트, 자유 텍스트, 이미지, 서명을 페이지 위에 추가한 뒤에는 “그려졌다”보다 “나중에 다시 고칠 수 있다”가 중요했다. 추가한 글자·문장·이미지·서명을 선택해 이동하고, 이미지와 서명은 크기를 바꾸며, 이미지는 자르기와 레이어 순서를 조절할 수 있게 했다.

오픈소스 앱의 이름표는 비밀이 아니다. 외부 PDF도 `/HwattakPDFKind` 같은 공개 key를 그대로 복사할 수 있으므로, 문자열을 “우리 주석이라는 증명”으로 사용하면 뷰어·학습 모드의 안전 경계를 위조할 수 있다. 에디팅 모드는 명시적인 넓은 편집 화면으로 유지하되, 뷰어·학습에서 이동·삭제할 때는 현재 PDFKit 세션에서 실제로 생성하거나 사용자가 명시 편집한 동일 객체인지 weak identity까지 다시 확인하도록 바꿨다. 저장 후 재개방이나 휴면 뒤에는 새 객체가 만들어지므로 안전 모드에서 자동으로 신뢰를 복원하지 않는 쪽을 선택했다.

에디팅 모드의 텍스트는 별도 주석 sheet를 거치지 않고 PDF 위를 클릭한 위치에서 바로 입력하도록 바뀌었다. 글꼴·크기·색상·정렬·배경을 조절하고, 앱이 만든 FreeText는 이중 클릭해 같은 인라인 경로로 고친다. 기존 글자를 선택해 “교체”할 때도 콘텐츠 스트림을 다시 쓰는 대신 원문 위에 FreeText를 올리는 시각적 오버레이이며, 원문은 검색·복사에 남고 보안 삭제가 아니라는 경고를 숨기지 않았다.

서명 선택 UI의 `×` 표식이 실제 서명 결과에 따라오는 문제처럼 작은 시각 버그도 사용 경험을 크게 망쳤다. 선택·삭제 장식은 편집 overlay에만 있고, 저장되는 서명 이미지는 투명한 획만 남도록 역할을 분리했다.

여기서 지켜야 할 표현도 정리했다. 현재 텍스트와 이미지는 PDF 원래 콘텐츠 스트림을 고치는 것이 아니라 표준 주석과 스탬프를 추가하는 방식이다. 손으로 그린 서명도 인증서·ByteRange를 사용하는 디지털 서명과는 다르다.

## 4막: 저장 실패와 실행 취소를 제품의 중심으로

편집 기능이 늘자 가장 무서운 문제는 저장이었다. “저장할 수 없습니다”라는 메시지가 뜨거나 앱을 닫을 때 아무 확인이 없다면 나머지 기능이 많아도 믿고 쓸 수 없다.

- 원본 덮어쓰기, 별도 저장, 취소의 명확한 흐름
- 닫기·창 종료·앱 종료 전 문서별 미저장 변경 확인
- 목적지와 같은 폴더의 검증된 임시 파일 교체를 우선하고, 파일 단위 권한에서는 사전·사후 검증 직접 쓰기로 호환하는 저장
- 열기·재개·저장 baseline을 비교해 다른 앱이 바꾼 원본의 조용한 덮어쓰기 차단
- 저장 성공 뒤에만 UI 상태와 clean checkpoint 갱신
- 펜뿐 아니라 주석·이미지·서명·양식·페이지 구조를 포함하는 `⌘Z`/`⇧⌘Z`
- 문서별 최대 22단계 델타 이력과 구조 편집 64페이지 비용 상한

22라는 숫자는 단순히 작은 배열 길이만 의미하지 않는다. 명령마다 PDF 전체 복사본을 저장하면 대형 PDF에서 22회도 감당할 수 없다. 실제 변경한 주석, 값, 좌표, 분리한 페이지만 보관하고 clean 탭이 휴면할 때 이력을 비워 PDFKit 객체 그래프를 놓아 주는 설계로 바뀌었다.

마일스톤 감사에서는 같은 원본을 Preview나 동기화 프로그램이 먼저 저장한 뒤 HwattakPDF가 오래된 메모리 문서로 덮어쓸 수 있는 위험도 확인했다. 이제 원본과 같은 위치에 저장하기 직전 coordinated transaction 안에서 열 때 기록한 파일 버전을 비교한다. 충돌하면 외부 파일 bytes는 그대로 두고 HwattakPDF의 dirty 편집도 메모리에 남겨, 사용자가 별도 저장으로 두 버전을 모두 보존할 수 있다. 전체 파일 hash나 실시간 `NSFilePresenter` 감시는 아니므로 의도적으로 metadata를 보존한 변경과 서버측 merge까지 해결한다고 표현하지 않는다.

## 5막: 앱을 닫아도 작업 공간을 되찾기

브라우저 같은 탭은 재실행 후 사라지면 의미가 반감된다. security-scoped bookmark와 원자 JSON manifest를 사용해 열린 파일, workspace, 탭 순서, 스택, 활성 페이지, 비교 배치와 분리 창 소속을 지연 복원하게 했다. 최근 문서는 최대 7개를 시작 화면에서 다시 열 수 있다.

다만 미저장 PDF 바이트를 자동 복구 저널로 보관하는 단계까지 간 것은 아니다. 종료 확인에서 저장하지 않고 버린 변경은 돌아오지 않는다. SwiftUI 공개 복원 API의 한계로 분리 창의 정확한 화면 위치와 크기도 기본값으로 돌아온다. 현재 복원 기능과 아직 없는 crash recovery를 같은 것으로 소개하지 않기로 했다.

기본 서명은 매번 다시 그리지 않도록 현재 macOS 사용자의 비동기화 Keychain에 벡터 획으로 저장한다. 이 서명은 기기 간 동기화하지 않으며, 정식 Developer ID/App Store 서명 전 ad-hoc 빌드에서는 안정적인 전용 access group까지 보장되지 않는다는 보안 경계도 문서화했다.

## 6막: 50~200MB 파일을 수십 개 열 때 버티기

“Rust나 Go로 다시 쓰면 빨라질까?”라는 질문도 있었다. 측정하기 전에 언어를 바꾸면 PDFKit이 차지하는 객체·타일 캐시와 메인 스레드 제약은 그대로이고 FFI 복사만 늘어날 수 있다. 먼저 실제 병목인 객체 수명을 줄였다.

- 활성 탭의 `PDFView`만 화면에 유지
- 기본 3개 resident 문서 예산과 깨끗한 비활성 탭 LRU 휴면
- warning/critical 메모리 압력에서 재생성 가능한 문서 해제
- 파일을 여러 개 열 때 최대 3개 정도만 병렬 검사하고 순서대로 설치
- 앱 전체 CPU·RSS 실측과 파일별 상대적 예상 부담을 구분해 표시
- OCR이 필요할 때만 대용량 파일 fingerprint 계산

정책 알고리즘의 작은 benchmark보다 중요한 것은 실제 50~200MB 자료 20~100개를 장시간 스크롤했을 때의 RSS, 렌더 지연, thermal 상태다. 민감정보를 제거한 실물 fixture가 없어 이 GUI 스트레스 측정은 아직 릴리스 전 수동 과제로 남아 있다.

## 7막: 로컬 OCR과 선택 가능한 외부 AI

스캔 PDF를 공부하려면 검색 가능한 텍스트가 필요하다. Apple Vision으로 한국어·영어·일본어를 한 페이지씩 로컬 인식하고, 페이지별 독립 체크포인트를 남겨 취소·재개할 수 있게 했다. 출력은 보이는 페이지 위에 보이지 않는 텍스트를 얹은 새 PDF다. 이 과정은 링크·폼·전자서명을 완전히 보존하는 범용 변환기가 아니므로 원본 보관이 필요하다.

재개 편의를 위해 체크포인트에는 인식한 텍스트와 위치가 Application Support의 평문 JSON으로 남는다. 현재 자동 만료나 앱 안의 정리 버튼이 없으므로 민감 문서의 보존 정책과 맞지 않을 수 있다. 로컬 처리가 곧 디스크에 흔적이 없다는 뜻은 아니며, 자동 보존 기한·문서별 삭제 UI와 안전한 정리 정책은 다음 마일스톤 과제다.

AI가 대세인 만큼 요약, 분석, 수학·과학 문제 풀이, 채우기 초안, 관련 PDF 찾기, 웹 조사를 연결했다. 그러나 AI를 로컬 기능의 필수 조건으로 만들지는 않았다.

- OpenAI, Claude, Gemini, DeepSeek, Qwen, OpenAI-compatible 설정
- 사용자가 직접 넣은 API 키를 Keychain에 보관
- 선택/현재/대표 페이지의 제한된 텍스트만 전송 전 미리보기
- AI 답변은 자동으로 PDF를 바꾸지 않고 사용자가 확인한 자유 텍스트 주석으로만 추가
- 열린 탭과 최근 문서를 대상으로 하는 로컬 관련 PDF 검색
- OpenAI 웹 출처와 원격 MCP 도구의 호출별 승인

문서 속 명령이 모델을 속일 수 있다는 prompt injection 문제 때문에 PDF 텍스트를 신뢰하지 않는 데이터로 감싸고, MCP는 서버·도구·인자를 매번 보여 준 뒤 승인받도록 했다.

## 8막: 공부 도구다운 전체 문서 검색

초기 검색창은 다음/이전만 움직이는 수준이라 장문의 문서를 검토하기 어려웠다. 현재는 `⌘F`로 전체 문서를 페이지 단위로 검색하고, 사이드바에서 모든 결과의 페이지·문맥·일치 개수를 훑을 수 있다.

- Enter/Shift+Enter 순환 이동과 현재 결과 강조
- 페이지 썸네일의 일치 배지
- 한국어·영어·일본어·중국어·아랍어 Unicode 정규화
- 대소문자, 발음 구별 부호, 전각/반각, 연속 공백, 줄바꿈 하이픈 보정
- 취소·진행률·부분 결과와 최대 20,000건 상한
- 텍스트 층이 없는 문서의 OCR 안내

수천 개의 `PDFSelection`을 보관하면 검색 자체가 메모리 문제를 만든다. 그래서 navigator에는 페이지와 UTF-16 범위만 두고 현재 선택 한 건만 PDFKit 객체로 지연 생성한다. 간체↔번체, 형태소·동의어·의미 검색까지 되는 것은 아니며, 스캔 문서는 먼저 OCR 사본이 필요하다.

## 9막: 하나의 PDF를 세 가지 목적으로 다루기

기능이 한 툴바에 계속 늘어나자 읽고 싶은 사람과 편집하려는 사람, 공부하려는 사람 모두가 불필요한 도구를 보게 됐다. 그래서 PDF를 복제하는 방식이 아니라 탭의 작업 목적만 바꾸는 세 모드를 만들었다. `⌃1`·`⌃2`·`⌃3`으로 전환하고, 마지막 모드는 세션과 함께 복원한다.

- 뷰어 모드: 읽기·선택·복사/붙여넣기, 주석 메모, 그래픽 서명, 번역·AI, 메모 후 공유
- 에디팅 모드: 인라인 FreeText, 이미지·서명 이미지 삽입, 그래픽 서명과 펜, 페이지 재정렬·회전·삭제·병합·추출
- 학습 모드: 번역·용어 설명·요약·풀이 과정·학습 포인트·퀴즈, 타이핑/펜 메모, 조절형 하이라이트·밑줄, 메모 후 공유

학습 AI 버튼은 네트워크를 바로 호출하지 않는다. 먼저 공급자와 개발자 API 키가 있어야 하고, 선택문 또는 현재 페이지의 bounded 문맥과 endpoint를 미리 보여 준 뒤 사용자가 명시적으로 동의해야 요청한다. 메모 공유도 선택문 최대 4,000자와 메모 최대 8,000자의 일반 텍스트 snapshot만 macOS 공유 시트로 넘기며 PDF 파일과 경로는 포함하지 않는다.

마지막 사용성 점검에서는 뷰어·에디팅 툴바의 하이라이트 버튼이 사용자가 고른 색을 보지 않고 항상 기본 노랑을 쓰는 경로를 발견했다. 이제 버튼 옆 색상 견본에서 다음 하이라이트 색을 직접 고르고, 버튼·`⇧⌘H`·학습 팔레트가 같은 mode-aware 명령으로 들어간다. 내부에는 원래 하이라이트 Undo 이력이 있었지만 포인터 사용자가 발견하기 어려웠으므로, 툴바에도 현재 문서의 22단계 이력을 사용하는 실행 취소·다시 실행 버튼을 함께 노출했다.

Apple Pencil은 Mac 앱에 직접 붙는 입력 장치처럼 소개하지 않았다. 현재 필기는 마우스·트랙패드, 또는 Sidecar가 전달한 Apple Pencil 포인터를 Ink로 받는 경로다. 학습 표식도 색상·두께·진하기를 저장하기 위해 appearance를 가진 표준 Stamp를 쓰므로 눈에 보이는 결과는 유지하지만 semantic Highlight/Underline은 아니다.

## 10막: “기능이 있다”에서 “다른 사람이 유지할 수 있다”로

사용하면서 발견된 중복 `설정…` 메뉴, 크기 조절이 안 되는 사이드바, 페이지 직접 이동 부재, 단축키와 도움말 불일치 같은 문제를 차례로 줄였다. 앱 안에는 실제 아이콘과 주요 단축키를 검색할 수 있는 사용법 창을 만들었다. 사용자 문구는 현재 10개 언어 리소스를 유지하며 VoiceOver와 RTL도 회귀 범위에 넣었다.

현재 저장소에는 기능별 XCTest가 수백 개 있고, 검색·저장·실행 취소·탭 수명·세션 복원·보안 저장소·AI 경계를 코드로 고정한다. 자동 테스트는 중요한 안전망이지만 PDFKit 렌더링, 실제 트랙패드, File Provider, 다양한 생성기의 PDF 호환성까지 모두 대신하지는 못한다. 그래서 이번 마일스톤에는 수동 점검표, 기여 가이드, 보안 정책과 정직한 미구현 목록을 함께 남긴다.

## 지금 도달한 곳

0.7.0은 “완성된 상용 PDF 엔진”이 아니라, 로컬 우선 PDF 작업 공간을 뷰어·에디팅·학습이라는 세 가지 목적에 맞춰 정리한 중간 마일스톤이다. 읽기·탭·스택·분할 비교·인라인 FreeText·페이지 조립·주석·서명·학습 도구·OCR·전체 검색·선택형 AI까지 한 흐름으로 연결되었다. 원자 교체 우선 저장과 검증 fallback, 실행 취소, 휴면, Keychain, bounded 공유와 전송 승인처럼 눈에 덜 띄지만 신뢰에 필요한 기반도 생겼다.

동시에 다음 한계를 숨기지 않는다.

- 인라인 텍스트와 시각적 교체는 FreeText 오버레이이며 기존 콘텐츠 스트림의 본문·이미지 객체를 직접 수정하거나 삭제하지 않음
- 시각적 텍스트 교체는 가린 원문이 검색·복사에 남으므로 secure redaction이 아님
- 조절형 학습 하이라이트·밑줄은 외형 보존용 표준 Stamp이며 semantic Highlight/Underline이 아님
- Apple Pencil 필기는 Sidecar 포인터 경유이며 Mac 직접 연결·PencilKit 입력이 아님
- 인증서 기반 디지털 서명과 안전한 redaction은 아직 없음
- 자동 복구 저널과 암호 PDF 폭넓은 검증은 아직 없음
- OCR 인식문 체크포인트의 자동 보존 기한·암호화·앱 내 삭제 UI는 아직 없음
- 실제 초대형 자료 20~100개 GUI 스트레스와 다양한 외부 PDF 뷰어 상호운용성 검증이 더 필요함
- AI는 공급자·개발자 API 키와 요청별 명시 동의가 필요하며, 답변 정확성과 공급자 데이터 정책은 앱이 보증할 수 없음
- 라이선스와 소개 그림 재배포 권리가 정리되기 전에는 법적으로 오픈소스 공개 준비가 끝난 것이 아님
