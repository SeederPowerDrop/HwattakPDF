# 4장 페이지 선택과 실행 취소

이 장을 마치면 `1, 3-5, 8`이라는 문자열(string)을 앱이 어떻게 해석하는지 설명하고, 실행 취소와 저장 상태를 종이에 직접 추적할 수 있습니다. 알고리즘(algorithm)은 문제를 해결하기 위한 절차입니다. 입력을 정해진 규칙으로 변환하거나 순서에 따라 상태를 바꾸는 과정도 알고리즘에 해당합니다.

읽을 원문은 [OCRPageSelection.swift](../../Sources/HwattakPDF/Models/OCRPageSelection.swift), [PDFEditHistory.swift](../../Sources/HwattakPDF/Models/PDFEditHistory.swift), [PDFWorkspaceState.swift](../../Sources/HwattakPDF/Models/PDFWorkspaceState.swift)입니다. 파일 안에서 `[학습 04]` 또는 이 장의 함수 이름을 검색하세요.

## 작은 예제로 시작하기

범위나 중복이 없는 입력 `2, 4`부터 생각해 보세요. 사용자가 입력창에 적은 것은 숫자 목록이 아니라 글자로 된 문자열(string)입니다. 쉼표를 기준으로 나누고, 각 글자를 숫자로 바꾼 다음, 내부 위치에 맞게 1을 뺍니다.

| 순서 | 처리한 뒤의 값 | 한 일 |
| --- | --- | --- |
| 입력 | `"2, 4"` | 사용자가 입력한 글자를 받음 |
| 나누기 | `"2"`, `"4"` | 쉼표로 나누고 양옆 공백을 정리함 |
| 숫자로 바꾸기 | `2`, `4` | 계산할 수 있는 정수로 바꿈 |
| 위치로 바꾸기 | `1`, `3` | 각각 1을 뺌 |
| 결과 | `[1, 3]` | 선택할 위치를 목록으로 반환함 |

이 표는 개념을 익히기 위한 모형입니다. 실제 코드는 숫자로 바꿀 수 있는지, 문서 안에 있는 번호인지도 검사합니다. 글자 `"a"`를 받았다고 임의로 0으로 바꾸면 안 됩니다. 잘못된 입력은 오류로 알려 줍니다.

**먼저 해 보세요.** 5쪽짜리 문서에서 `1, 5`는 `[0, 4]`가 됩니다. `1, 6`은 `[0, 5]`를 결과로 내면 안 됩니다. 6쪽이 없기 때문에 오류가 되어야 합니다. 이 두 예를 설명할 수 있으면 4.1~4.3절을 읽으세요. 실행 취소는 별개의 기능이므로 4.5절부터 다음 공부 시간에 읽어도 됩니다.

## 4.1 사람의 페이지 번호와 배열의 인덱스

사람은 PDF의 첫 장을 1페이지라고 부릅니다. 코드의 배열(array)은 첫 원소의 위치를 인덱스(index) 0으로 나타냅니다. 따라서 8페이지의 내부 인덱스는 7입니다. 여기서는 PDF에 인쇄된 쪽수나 로마 숫자가 아니라, 뷰어에 표시된 PDF 페이지의 실제 순서를 기준으로 합니다.

| 사용자 입력 | 내부 값 | 의미 |
| --- | --- | --- |
| `1` | `0` | 첫 페이지 |
| `3-5` | `2, 3, 4` | 세 번째부터 다섯 번째까지 |
| `1, 3-5, 8` | `[0, 2, 3, 4, 7]` | 다섯 페이지를 선택 |

이 변환을 화면마다 반복하면 어느 곳에서는 1을 두 번 빼는 문제가 생깁니다. 사용자 입력을 해석하는 단계에서 한 번 변환하고, 이후 내부 처리에서는 인덱스로 통일하는 것이 좋습니다. 사용자에게 표시할 때 다시 1을 더합니다.

## 4.2 반환형이 알려 주는 설계

`OCRPageSelection.resolve`의 선언에는 `throws -> [Int]?`가 있습니다. 반환 타입(return type)은 정수 배열의 옵셔널(Optional)인 `[Int]?`입니다. `Int`는 정수, `[Int]`는 정수 배열을 뜻하고, `?`는 값이 없을 수도 있음을 나타냅니다. `throws`는 반환 타입의 일부가 아니라, 잘못된 입력을 받으면 함수가 오류를 던질 수 있다는 표시입니다.

이 앱은 `nil`을 **전체 문서 선택**을 나타내는 값으로 정했습니다. 빈 배열 `[]`과 뜻이 다릅니다. 이는 Swift 언어가 정한 의미가 아니라, 이 함수를 제공하는 쪽과 사용하는 쪽이 함께 따르는 API 계약(API contract)입니다. `OCRConfiguration.resolvedPageIndexes(pageCount:)`는 이후 이 선택을 실제 인덱스 배열로 확정합니다.

다음은 원문에서 가져온 분기입니다.

```swift
guard pageCount > 0 else { throw OCRPageSelectionError.emptySelection }
switch scope {
case .all:
    return nil
case .current:
    guard currentPageIndex >= 0, currentPageIndex < pageCount else {
        throw OCRPageSelectionError.outOfBounds(pageCount: pageCount)
    }
    return [currentPageIndex]
case .custom:
    // 실제 원문에서는 아래에 문자열 해석 코드가 이어진다.
```

마지막 중괄호와 나머지 구현을 생략한 **발췌**입니다. 독립 실행 프로그램으로 붙여 넣는 코드가 아닙니다. `guard`를 읽을 때는 “이후 코드가 참이라고 믿어도 되는 조건은 무엇인가?”를 생각하세요. 전체 선택이어도 페이지가 0개인 문서는 먼저 거부합니다.

## 4.3 문자열을 작은 단계로 해석하기

사용자가 직접 입력한 페이지 목록을 분석하는 파싱(parsing)은 다음 순서로 진행됩니다. 기호를 같은 형태로 맞추는 앞부분의 처리를 정규화(normalization)라고 합니다.

1. 앞뒤 공백을 없애고 빈 입력을 거부합니다.
2. 여러 종류의 대시와 `~`를 `-`로, 전각 쉼표를 `,`로 통일합니다.
3. 쉼표로 `1`, `3-5`, `8` 같은 항목을 나눕니다.
4. 각 항목을 하이픈으로 나누어 숫자 하나 또는 양 끝 숫자 둘을 얻습니다.
5. ASCII 문자 코드의 숫자 `0`부터 `9`로만 구성되는지, `Int`로 바꿀 수 있는지, 문서 범위 안인지 검사합니다.
6. 양 끝이 오름차순인지 확인한 뒤 범위를 펼칩니다.
7. 각 번호에서 1을 빼 집합에 넣고, 마지막에 정렬합니다.

원문의 `split(separator: ",", omittingEmptySubsequences: false)`에서 `false`는 작은 설정처럼 보이지만 중요한 의미가 있습니다. `1,,2`를 나누면 가운데 빈 항목이 남습니다. 그래야 잘못된 입력으로 판정할 수 있습니다. 빈 항목을 버리면 사용자의 실수를 조용히 `1,2`로 바꾸게 됩니다.

`Set<Int>`는 같은 숫자를 한 번만 보관하는 집합(set)입니다. `3,3,2-4`에 3이 여러 번 나와도 같은 페이지를 여러 번 선택하지 않습니다. `Set`은 원소를 꺼내는 순서를 보장하지 않으므로 마지막에 `sorted()`로 정렬합니다. Rust 실습에서는 정렬과 중복 제거를 함께 제공하는 `BTreeSet`을 사용해 두 설계를 비교합니다.

### 입력을 따라가 보는 표

문서가 12페이지이고 입력이 `8, 3-5, 4`라고 가정해 보세요.

| 단계 | 현재 항목 | 집합에 들어 있는 내부 인덱스 |
| --- | --- | --- |
| 첫 번째 항목 | `8` | `{7}` |
| 두 번째 항목 | `3-5` | `{2, 3, 4, 7}` |
| 세 번째 항목 | `4` | `{2, 3, 4, 7}` |
| 결과 정렬 | 전체 | `[2, 3, 4, 7]` |

표의 집합은 읽기 좋게 정렬해 썼습니다. 실제 집합의 순서를 보장한다는 뜻은 아닙니다.

### 검사를 먼저 하는 이유

`1-999999999`를 먼저 펼치고 나중에 범위를 검사하면 배열이나 집합이 매우 커질 수 있습니다. 현재 코드는 양 끝이 `1...pageCount`에 들어오는지 확인한 뒤 `first...last`를 순회합니다. 입력 처리 순서 자체가 메모리 사용을 제한합니다.

정확히 말하면 **중복을 제거한 결과 집합의 크기**는 문서 페이지 수 이하입니다. 같은 큰 범위를 수없이 반복한 매우 긴 입력의 처리 시간까지 페이지 수로 제한되는 것은 아닙니다. 성능을 설명할 때 결과 크기와 실행 횟수를 구분해야 합니다.

`numbers.last!`도 만나게 됩니다. 여기서 `!`는 값이 반드시 있다고 가정하고 옵셔널에서 값을 꺼내는 강제 언래핑(forced unwrapping)입니다. 이 코드에서는 앞에서 항목 수가 1 또는 2임을 확인하고 변환 실패 시 즉시 오류를 던졌으므로, 그 지점의 배열은 비어 있지 않습니다. `!`가 보이면 따라 쓰기보다 값이 있다는 가정을 보장하는 앞선 검사를 찾으세요.

## 4.4 반대 방향으로 바꾸는 함수

`compactDescription`은 `[0, 2, 3, 4, 7]`을 `1, 3-5, 8`로 바꿉니다. 먼저 중복·유효하지 않은 값을 정리하고 정렬한 뒤, 연속된 구간의 시작과 끝만 기억합니다.

현재 구간이 `2...4`인데 다음 인덱스가 7이면 연속된 구간이 끝난 것입니다. `3-5`라는 사용자용 문자열을 저장하고, 새 구간을 7에서 시작합니다. 반복문(loop)이 끝난 뒤 마지막 구간도 한 번 저장해야 합니다. 마지막 묶음을 빠뜨리는 실수는 반복 처리가 끝나는 지점에서 자주 발생합니다.

두 변환을 연달아 실행해 원래 의미가 유지되는지 확인하는 것을 **왕복 검사**(round-trip test)라고 합니다. 유효한 인덱스 집합을 문자열로 바꾼 다음 다시 해석하면 원래 선택을 얻어야 합니다. 단, 입력 순서와 중복까지 복원하는 것은 아닙니다. 함수가 의도적으로 만든 정렬·중복 제거 결과를 비교합니다.

## 4.5 실행 취소는 과거 파일을 전부 복사하는 기능일까

이 앱의 `PDFEditHistory`는 편집할 때마다 PDF 전체를 복사하지 않습니다. 하나의 변경에 대해 실행 취소(undo) 동작과 다시 실행(redo) 동작을 저장합니다. 이처럼 작업을 하나의 명령으로 묶어 다루는 설계를 명령 패턴(command pattern)이라고 부릅니다.

하이라이트를 예로 들면, 이미 추가한 PDF 주석(annotation)을 제거하는 동작이 실행 취소이고 그 주석을 다시 추가하는 동작이 다시 실행입니다. 원문의 `registerAnnotationAdditions`는 주석과 페이지의 관계가 예상대로인지 확인한 뒤 이 두 동작을 등록합니다. 이 함수의 클로저(closure)는 실제로 `document`도 참조합니다. 따라서 “변경분을 기록한다”는 설명이 문서 객체에 대한 참조(reference)까지 모두 없앤다는 뜻은 아닙니다. 핵심은 PDF 파일 전체의 바이트(byte)를 매번 복사하지 않는다는 점입니다.

여기서 클로저는 “전달하거나 저장할 수 있는 코드와 그 코드가 사용하는 주변 값”입니다. 주변 값을 사용하도록 기억하는 것을 캡처(capture)라고 합니다. 이력을 소유한 `PDFWorkspaceState`를 클로저가 강하게 참조하면 `상태 → 이력 → 클로저 → 상태`로 이어지는 강한 참조 순환(strong reference cycle)이 생길 수 있습니다. 서로를 계속 보유하기 때문에 필요 없어져도 객체가 해제되지 않을 수 있습니다. 따라서 클로저가 필요한 페이지·주석·값만 보관하는지 살펴봐야 합니다.

`register`는 편집을 처음 실행하는 함수가 아닙니다. **이미 성공한 편집**을 이력에 올립니다. 호출 전에 실제 문서를 바꾸고, 성공한 후 역동작을 등록한다는 순서를 구분하세요.

## 4.6 두 개의 스택과 저장 지점

스택(stack)은 나중에 넣은 항목을 먼저 꺼내는 자료구조(data structure)입니다. 이런 순서를 후입선출(last in, first out, LIFO)이라고 합니다. 이 앱은 실행 취소용 스택과 다시 실행용 스택을 각각 사용합니다. 아래 표에서 오른쪽 끝이 다음에 꺼낼 항목입니다.

| 동작 | undo 스택 | redo 스택 | 현재 문서 |
| --- | --- | --- | --- |
| 처음 | `[]` | `[]` | 원본 |
| A 하이라이트 | `[A]` | `[]` | A 적용 |
| B 메모 | `[A, B]` | `[]` | A와 B 적용 |
| 실행 취소 | `[A]` | `[B]` | A만 적용 |
| 다시 실행 | `[A, B]` | `[]` | A와 B 적용 |
| 실행 취소 후 C 편집 | `[A, C]` | `[]` | A와 C 적용 |

마지막 줄에서 B를 지우는 이유는 실행 취소한 자리에 새로운 편집 C가 생겼기 때문입니다. B가 전제로 삼았던 문서 상태와 달라졌으므로, C 이후에도 B를 그대로 다시 적용할 수 있다고 가정하면 안 됩니다.

저장 여부를 “실행 취소 스택이 비었는가?”로 판단하면 문제가 생깁니다. 편집한 뒤 저장해도 실행 취소는 계속 가능해야 하기 때문입니다. 현재 구현은 상태마다 UUID(universally unique identifier)라는 식별자를 붙이고 마지막으로 저장한 상태의 UUID를 따로 기억합니다.

```swift
var isAtSavedState: Bool { currentStateID == savedStateID }

func markSaved() {
    savedStateID = currentStateID
}
```

원문의 발췌입니다. UUID는 이력의 위치를 구별하는 이름이며, PDF 내용으로 계산한 해시(hash)가 아닙니다. 저장 지점으로 실행 취소하면 저장 상태와 일치하는 상태(clean state)가 되고, 거기서 다시 편집하거나 다시 실행하면 미저장 상태(dirty state)가 됩니다. 화면의 `isDirty`는 `synchronizeHistoryPresentation()`에서 이 비교를 바탕으로 갱신합니다.

## 4.7 실패하는 실행 취소도 생각하기

원문은 `try command.undoMutation()`이 성공한 뒤 명령을 한 스택에서 다른 스택으로 옮깁니다. 실행 취소가 실패했는데 명령부터 제거하면 다시 시도할 기회를 잃고, 이력이 실제 문서 상태와 어긋납니다. `defer` 블록은 함수가 정상 종료되거나 오류를 던져도 실행되어 `isApplyingCommand` 값을 되돌립니다.

다만 이력 클래스가 이미 일어난 변경을 자동으로 롤백(rollback), 즉 이전 상태로 복구해 주는 것은 아닙니다. 실행 취소 클로저가 문서를 일부 바꾼 뒤 실패하면 스택만 유지됩니다. 따라서 실제 변경 함수는 필요한 조건을 먼저 모두 검사하고, 문서를 변경하는 도중에 실패해도 일관된 상태를 유지하도록 설계해야 합니다.

기본 한도는 명령 22개와 보관 페이지 비용(retained page cost) 64입니다. 보관 페이지 비용은 실행 취소를 위해 문서 밖에 따로 보유한 페이지 수를 기준으로 한 값이며, 바이트 단위로 측정한 정확한 메모리 사용량은 아닙니다. 한 번에 많은 페이지를 삭제한 경우에는 한도를 넘더라도 한 개의 명령으로 남겨 즉시 되돌릴 수 있게 합니다. 이후 편집이 쌓이면 오래된 이력을 정리합니다. 사용자가 되돌릴 기회와 메모리 사용량을 함께 고려한 규칙입니다.

## 4.8 직접 풀어 보기

1. 10페이지 문서에서 `5, 2-4, 3`의 결과를 쓰세요. `0`, `4-2`, `1,,2`는 각각 왜 실패할까요?
2. A 편집 후 저장하고, B 편집 후 실행 취소를 한 번 했습니다. 미저장 표시와 실행 취소 스택은 어떤 상태일까요?
3. `register`에서 `redoStack.removeAll`을 없애면 어떤 사용자 동작으로 문제가 드러날까요?

### 해설

1. 결과는 `[1, 2, 3, 4]`입니다. `0`은 사용자용 번호의 범위를 벗어나고, `4-2`는 역순이며, `1,,2`는 빈 항목을 포함합니다. 각각 실패 이유를 말로 구분한 뒤 테스트 이름으로 바꿔 보세요.
2. A를 저장한 상태로 돌아왔으므로 `isDirty`는 `false`입니다. 실행 취소 스택은 여전히 A를 담고, 다시 실행 스택에는 B가 있습니다. 저장과 이력 삭제가 다르다는 사례입니다.
3. A와 B를 적용한 뒤 B를 실행 취소하고 C를 새로 편집한 다음 다시 실행을 누르는 경우입니다. B의 전제 조건이 C로 달라졌는데도 이전 편집 B를 적용하려 할 수 있습니다.

### 완료 기준

원문을 보면서 `nil`, `Set`, `sorted()`, `beforeStateID`, `savedStateID`, `defer`가 각각 지키는 규칙을 한 문장씩 설명할 수 있으면 다음 장으로 넘어가세요. [6장 테스트](06-TESTING.md)에서는 이런 설명을 자동 검사로 바꿉니다.
