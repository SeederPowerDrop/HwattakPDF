# 5장 파일 저장과 OCR

이 장의 목표는 저장 버튼을 누른 뒤 일어나는 일, 오래 걸리는 작업이 시작되고 끝나는 과정, OCR의 좌표와 결과 보존 방식을 이해하는 것입니다. 좋은 문서 앱은 결과를 화면에 보여 주는 데서 끝나지 않습니다. 실패했을 때 사용자의 문서와 편집 내용을 어떻게 보존할지도 설계합니다.

중심 파일은 [AtomicPDFWriter.swift](../../Sources/HwattakPDF/Services/AtomicPDFWriter.swift), [VisionOCRService.swift](../../Sources/HwattakPDF/Services/VisionOCRService.swift), [PDFWorkspaceState.swift](../../Sources/HwattakPDF/Models/PDFWorkspaceState.swift)입니다. 보조 파일로 [PDFSourceFileVersion.swift](../../Sources/HwattakPDF/Services/PDFSourceFileVersion.swift), [PDFOCRApplication.swift](../../Sources/HwattakPDF/Services/PDFOCRApplication.swift), [SearchablePDFExporter.swift](../../Sources/HwattakPDF/Services/SearchablePDFExporter.swift)를 펼쳐 두세요.

## 처음 읽는 순서

먼저 **화면에 보이는 편집과 파일에 기록된 내용은 다를 수 있다**는 점만 이해하세요. 메모리(memory)는 실행 중인 프로그램이 데이터를 다루는 공간입니다. 저장 장치의 파일은 앱이 종료된 뒤에도 다시 읽을 수 있도록 남기는 기록입니다.

| 사용자의 행동 | 메모리에서 다루는 문서 | 저장한 PDF 파일 |
| --- | --- | --- |
| PDF를 엽니다 | 파일을 읽어 문서를 다룹니다 | 기존 내용 |
| 하이라이트를 추가합니다 | 하이라이트가 추가됨 | 아직 기존 내용 |
| 저장에 성공합니다 | 하이라이트가 있음 | 하이라이트가 반영됨 |
| 저장에 실패합니다 | 편집 내용을 보존해야 함 | 실패만으로 상태를 단정할 수 없음 |

마지막 줄이 중요합니다. 안전한 저장 절차는 기존 파일을 지키려고 하지만, 직접 덮어쓰는 도중 실패하면 파일이 일부만 기록될 수도 있습니다. 그래서 성공한 것을 확인한 뒤에만 “저장됨”으로 표시해야 합니다. 자동 저장이나 복구 사본도 별도의 구현이며, 메모리의 편집이 저절로 파일에 남는다는 뜻은 아닙니다.

첫 독서에서는 5.1~5.2절의 저장 순서와 5.5절의 OCR 흐름을 읽으세요. OCR은 사진 속 글자를 찾아 검색할 수 있는 글자로 만드는 작업이라고 먼저 이해하면 됩니다. `Task.detached`, 체크포인트, 좌표 변환의 세부 사항은 두 번째에 읽어도 됩니다.

**확인해 보세요.** 하이라이트가 화면에 보이는데 저장 오류가 나타났습니다. 앱이 “저장됨”이라고 표시해도 될까요? 안 됩니다. 화면에서 편집을 확인한 것과 파일 기록의 성공을 확인한 것은 서로 다른 일입니다.

## 5.1 메모리의 문서와 디스크의 파일

화면에서 하이라이트(highlight)를 추가하면 먼저 메모리의 `PDFDocument`와 `PDFAnnotation`이 바뀝니다. 파일에 이미 반영됐다는 뜻은 아닙니다. 저장은 객체(object)로 표현된 문서를 파일에 기록할 바이트(byte)로 바꾸는 **직렬화**(serialization) 과정입니다.

저장 함수의 성공은 최소한 세 가지를 의미해야 합니다. PDF를 쓸 수 있어야 하고, 다시 읽을 수 있어야 하며, 그 결과가 사용자가 승인한 목적지에 있어야 합니다. 메모리에만 남은 편집을 “저장됨”이라고 표시하면 사용자는 안전하다고 믿고 앱을 종료할 수 있습니다.

`PDFWorkspaceState.saveSynchronously(as:)`는 성공 여부를 `Bool`로 돌려줍니다. 창을 닫거나 앱을 종료하는 코드가 저장 실패를 확인하고 멈출 수 있도록 하기 위해서입니다. `@discardableResult`는 반환값(return value)을 사용하지 않을 때 나오는 컴파일러(compiler) 경고를 생략할 뿐, 결과 확인이 필요 없다는 의미는 아닙니다.

## 5.2 저장 흐름을 여섯 단계로 읽기

1. **편집 확정**: `prepareForDeactivation()`으로 페이지 위에서 직접 편집 중인 인라인 텍스트(inline text)와 현재 양식 입력을 문서 객체에 반영합니다. 별도의 검토 창인 시트(sheet)에서 아직 적용하지 않은 초안까지 저장하는 것은 아닙니다.
2. **허용 여부 검사**: 문서와 저장 위치가 있는지, 보안 정책상 이 저장 경로를 허용하는지 확인합니다.
3. **외부 변경 검사**: 같은 원본에 저장할 때는 열었던 파일의 기준 버전과 현재 버전을 비교합니다.
4. **직렬화와 결과 검사**: `AtomicPDFWriter`가 임시 PDF를 만들고 다시 열어 검사합니다.
5. **최종 교체**: 목적지가 중간에 바뀌지 않았는지 다시 확인한 뒤 교체 또는 이동합니다.
6. **상태 갱신**: 성공 후에만 파일 버전과 저장 지점을 갱신합니다.

이 순서를 코드에서 찾으려면 `saveSynchronously`, `overwriteDocument`, `AtomicPDFWriter.write`, `markSaved`를 차례대로 검색하세요. 파일 이름을 외우는 것보다 어떤 함수가 어느 단계의 책임을 지는지 찾는 연습이 중요합니다.

## 5.3 원자적 교체와 호환 경로

**원자적 교체**(atomic replacement)는 파일을 읽는 쪽에서 교체 중간 상태가 아니라 교체 전이나 교체 후의 완성된 파일을 보도록 하는 방식입니다. 이 앱은 기본적으로 목적지와 같은 폴더에 임시 PDF를 만든 뒤 검증하고 원본과 교체합니다. 임시 파일을 쓰다가 실패하면 기존 파일을 직접 덮어쓰지 않고 멈출 수 있습니다.

원문의 핵심 호출 순서는 다음과 같습니다. 조건과 오류 처리를 생략한 **구조 설명용 발췌**입니다.

```swift
try validatePDF(
    at: temporary,
    expectedPageCount: document.pageCount,
    validateSerializedDocument: validateSerializedDocument
)
try validateStagedPDF?(temporary, document.pageCount)
try validateDestinationBeforeCommit?()
try destinationPrecondition.validate()
```

`validateDestinationBeforeCommit`은 “교체 직전 한 번 더 검사해 달라”는 클로저(closure)입니다. 클로저는 실행할 코드와 그 코드가 사용하는 주변 값을 함께 다루는 기능입니다. 큰 PDF를 직렬화하는 사이에 다른 앱이 파일을 바꿀 수도 있기 때문에 시작할 때 한 검사만으로는 부족합니다.

macOS에서 사용자가 선택한 파일 하나에 대한 접근 권한이 그 옆에 새 파일을 만들 권한까지 주지는 않을 수 있습니다. 현재 구현은 이런 권한 문제에 한해 검증된 메모리 데이터를 직접 쓰는 대체 처리 경로(fallback)를 둡니다. 이 교재에서는 이를 “호환 경로”라고 부릅니다. 이 경로는 쓰기 전후에 검사를 하지만, 쓰는 도중 앱의 프로세스(process)가 종료되거나 입출력(input/output, I/O)이 실패하면 기존 파일을 완전히 보존한다고 보장할 수 없습니다.

따라서 `AtomicPDFWriter`라는 이름만 보고 “모든 저장이 항상 원자적이다”라고 설명하면 틀립니다. 디스크 용량 부족, 잘못된 PDF, 외부 수정 충돌 같은 다른 오류를 직접 덮어쓰기 경로로 우회하지 않는 것이 중요한 설계입니다. 보호된 일부 내보내기는 기존 목적지에 대한 직접 덮어쓰기 자체를 제한합니다.

파일이 다시 열리고 페이지 수가 일치하는지는 유용한 최소 검사입니다. 다만 이 검사만으로 모든 글꼴·링크·주석이 완전히 보존됐다고 할 수는 없습니다. 특정 기능이 보존됐는지 확인하려면 그 기능을 대상으로 하는 테스트가 더 필요합니다.

## 5.4 외부 변경과 자원 수명

같은 PDF를 미리보기 앱에서도 수정했다고 생각해 보세요. 우리 앱의 메모리에는 이전 파일에서 출발한 편집이 있습니다. 지금 그대로 덮어쓰면 다른 앱의 변경을 잃을 수 있습니다.

현재 구현은 파일 크기·수정 시각·파일 시스템(file system)의 식별 정보로 기준 버전을 추적합니다. 파일 접근을 조정하는 `NSFileCoordinator`와 교체 직전의 최종 확인을 함께 사용해 우발적인 덮어쓰기를 막습니다. 이는 실시간 변경 감시, 내용 병합, 암호학적인 파일 인증과는 범위가 다릅니다. 충돌을 발견하면 메모리의 편집 내용을 유지해 다른 파일로 저장할 수 있게 합니다.

`SecurityScopedAccess`는 파일 접근의 시작과 끝을 묶는 객체입니다. 객체가 살아 있는 동안 접근을 유지하고 필요가 없어지면 정리하는 **자원 수명 관리**(resource lifetime management)의 사례입니다. Rust의 소유권(ownership)과 `Drop`을 공부할 때도 자원을 누가 보유하고 언제 해제하는지 살펴보게 됩니다.

## 5.5 OCR은 글자 인식과 PDF 만들기의 조합

**광학 문자 인식**(optical character recognition, OCR)은 스캔 이미지에서 글자와 위치를 추정하는 과정입니다. 이미 검색 가능한 텍스트가 들어 있는 PDF에서 텍스트를 추출하는 일과 구분해야 합니다.

현재 앱의 경로를 데이터 종류로 나누면 다음과 같습니다.

```text
화면의 PDFDocument
    -> 작업 전용 PDF 스냅샷 파일
    -> 한 페이지의 이미지
    -> Vision 인식 결과: 문자열 + 위치 상자
    -> 페이지별 체크포인트
    -> 결과 검증
    -> 현재 PDF에 적용 또는 새 PDF로 저장
```

Vision은 글자 인식 기능을 제공하는 Apple의 프레임워크(framework)입니다. 인식 결과를 검색 가능한 PDF로 만드는 일은 이 앱의 내보내기 구성 요소(exporter)가 맡습니다. 외부 AI 서비스에 문서를 전송하지 않고 Mac에서 처리합니다. 선택한 언어를 인식할 수 있는지는 현재 Mac의 Vision 지원 언어 목록으로 확인합니다.

**스냅샷**(snapshot)은 작업 시작 시점의 문서 내용을 고정해 둔 사본입니다. 화면에서 사용하는 `PDFDocument`와 백그라운드(background) 작업이 같은 객체를 동시에 수정하지 않도록 작업용 PDF를 따로 엽니다. 복사에는 시간과 저장 공간이 들지만 객체 공유로 생길 수 있는 충돌을 줄입니다.

## 5.6 async와 백그라운드는 같은 말이 아니다

비동기 함수(asynchronous function)를 나타내는 `async`는 함수가 도중에 실행을 양보했다가 이어질 수 있다는 표시입니다. `await`는 그렇게 일시 중단될 가능성이 있는 호출 지점을 표시합니다. 이 키워드를 붙이는 것만으로 무거운 계산이 자동으로 다른 실행 영역으로 이동하지는 않습니다. [Swift 공식 동시성 설명](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/concurrency/)에서 이 언어 개념을 더 읽을 수 있습니다.

이 앱의 상태는 `@MainActor`에서 관리합니다. 화면 상태를 바꾸는 코드가 서로 충돌하지 않도록 액터 격리(actor isolation) 규칙을 적용하기 위해서입니다. `VisionOCRService.recognize`는 호출한 곳의 액터 격리를 상속하지 않는 분리 작업(detached task)을 `Task.detached`로 만듭니다. 이 작업 안에서 작업용 PDF를 열고 계산량이 많은 렌더링(rendering)과 인식을 수행합니다. 렌더링은 문서 데이터를 실제 이미지로 그리는 과정입니다. 진행률은 `completed`, `total`, `currentPage` 같은 작은 값으로 전달합니다.

이 구조가 모든 PDFKit 객체를 여러 스레드(thread)에서 자유롭게 공유해도 된다는 뜻은 아닙니다. 스레드는 프로그램 안에서 코드를 실행하는 흐름입니다. 이 앱은 작업용 객체를 분리하고 각 객체에 접근하는 코드를 제한합니다. `@MainActor`도 메모리 사용량이나 오래 걸리는 동기 함수(synchronous function)의 실행 시간을 자동으로 줄여 주지는 않습니다.

### 취소도 코드가 협력해야 한다

원문의 다음 부분은 OCR을 요청한 쪽에서 작업을 취소했을 때 그 요청을 분리 작업에도 전달합니다.

```swift
return try await withTaskCancellationHandler {
    try await worker.value
} onCancel: {
    worker.cancel()
}
```

`cancel()`은 실행을 강제로 중단하는 명령이 아니라 작업에 취소 요청을 표시하는 명령입니다. 실제 반복문에서 `Task.checkCancellation()`을 호출하고 취소가 확인되면 빠져나와야 합니다. 이렇게 작업 코드가 취소 요청에 직접 응답하는 방식을 **협력적 취소**(cooperative cancellation)라고 합니다. 이미 수행 중인, 시간이 오래 걸리는 시스템 호출이 즉시 멈춘다는 보장도 없습니다.

`defer`로 임시 파일을 지우는 코드도 찾아보세요. 정상 완료, 실패, 취소라는 여러 출구에서 공통 정리 작업을 빼먹지 않기 위해 사용합니다.

## 5.7 늦게 도착한 결과를 왜 버릴까

사용자가 OCR을 시작한 뒤 문서를 편집하거나 다른 문서를 열 수 있습니다. 이전 문서의 결과가 늦게 도착했는데 현재 문서에 적용하면 인식이 정확했어도 앱의 동작은 틀립니다.

`startOCR`는 시작할 때 문서 객체 식별자, `revision`, 파일 URL과 기준 버전, 실행 식별자 `runID`를 기록합니다. 완료되면 이 정보가 현재 상태와 맞는지 확인합니다. 리비전(revision)은 문서가 어느 변경 단계에 있는지 구분하는 값입니다. 내용을 요약한 해시(hash)나 저장 상태를 구분하는 UUID와는 역할이 다릅니다. 아래의 지문(fingerprint)은 입력 문서나 설정이 같은지 확인하기 위해 내용으로부터 계산한 식별 값입니다.

| 식별 정보 | 대답하는 질문 |
| --- | --- |
| `runID` | 아직 같은 OCR 요청인가? |
| `ObjectIdentifier(document)` | 아직 같은 메모리 문서 객체인가? |
| `revision` | 인식을 시작한 뒤 내용이 바뀌었나? |
| 문서 지문 | 체크포인트가 이 입력 내용에서 나왔나? |
| 설정 지문 | 언어·페이지 범위 등 인식 조건이 같은가? |

저장되지 않은 편집이 있는 문서는 디스크의 원본과 다를 수 있으므로 실제 작업 스냅샷의 지문을 사용해야 합니다. 원본에서 바뀐 내용이 없어 원본의 식별자를 재사용할 때도, 파일을 읽기 전후에 버전이 같은지 확인합니다. 이처럼 **데이터 자체가 정확한가**와 **지금 적용해도 되는 데이터인가**는 별개의 조건입니다.

## 5.8 체크포인트와 페이지별 결과

체크포인트(checkpoint)는 완료된 페이지의 인식 결과를 디스크에 남긴 기록입니다. 다시 실행할 때 문서와 설정이 일치하면 완료된 페이지의 결과를 재사용합니다. 페이지마다 저장하므로 매번 모든 결과를 다시 기록하지 않아도 됩니다.

체크포인트에는 인식 텍스트와 위치 정보가 들어갑니다. 암호를 보관하는 키체인(Keychain)에 저장하지 않고, 구조화된 텍스트 형식인 JSON(JavaScript Object Notation) 파일로 Mac에 저장합니다. 현재 설정 화면에서는 작업이 진행 중인지 확인하고 OCR 기록을 지울 수 있습니다. 저장 위치와 삭제 정책을 바꾸면 성능뿐 아니라 데이터 보존 방식도 달라집니다.

현재 선택 페이지 OCR은 문서 전체를 유지하며 새 인식 결과가 있는 페이지만 외관을 다시 그리고 검색 텍스트를 넣어 교체합니다. 기존 텍스트가 있던 페이지는 잘못된 옛 텍스트를 복제하지 않도록 이미지화하고, 기존 텍스트가 없는 페이지는 PDF 그리기 경로를 사용합니다. 선택하지 않은 페이지, 기존 텍스트로 건너뛴 페이지, 새 글자를 찾지 못한 페이지는 원래 페이지를 유지합니다. 이 세부 범위는 [최근 OCR 페이지 선택 기록](../OCR-PAGE-SCOPE-2026-09-25.md)과 실제 구현을 함께 확인하세요.

교체된 페이지에서는 기존 주석의 보이는 모습을 페이지에 합치는 평면화(flattening)가 일어납니다. 따라서 그 페이지의 기존 메모를 따로 편집하거나 링크·입력 양식을 기존처럼 사용하는 데 제약이 있습니다. 원래 페이지를 유지한 곳과 구분해야 합니다. 저장된 검색 가능 PDF가 원본의 모든 편집 구조까지 보존한다고 이해하면 안 됩니다.

## 5.9 좌표와 해상도

마우스 위치는 화면 좌표, 주석은 PDF 페이지 좌표, OCR이 찾은 글자의 경계 상자(bounding box)는 보통 0부터 1 사이의 정규화 좌표(normalized coordinates)로 표현합니다. 즉, 각 정보가 서로 다른 좌표 공간(coordinate space)을 사용합니다. 예를 들어 회전·자르기가 없는 폭 600, 높이 800인 페이지에서 폭 비율 `0.2`인 상자는 120포인트 폭입니다. 이것은 좌표 개념을 위한 단순 예시이며 앱에 그대로 복사할 완전한 변환식은 아닙니다.

실제 PDF에서는 페이지의 회전 각도와 크기, 화면에 보여 줄 영역인 자르기 상자(crop box)의 원점(origin)이 다를 수 있습니다. 원점은 좌표를 세기 시작하는 기준 위치입니다. 화면에 맞아 보이는 상자도 이런 조건을 빠뜨리면 저장한 페이지에서 어긋날 수 있습니다. 앱은 PDFKit의 좌표 변환 기능과 OCR 결과를 PDF로 조립하는 코드를 함께 사용합니다.

PDF의 기본 좌표 단위는 포인트(point)이며, 72포인트가 1인치입니다. DPI(dots per inch)는 인치당 점의 수를 뜻하며, 여기서는 PDF를 이미지로 만들 때의 해상도를 나타냅니다. 이미지 크기 상한이 적용되기 전에는 DPI를 두 배로 올리면 가로·세로 픽셀(pixel) 수가 각각 두 배가 되어 전체 픽셀 수는 대략 네 배가 됩니다. 실제 서비스는 이미지의 최대 변 길이와 전체 픽셀 수의 상한으로 크기를 제한합니다. 메모리 사용량과 처리 시간에는 계산 결과를 재사용하는 캐시(cache), 색상 형식, 인식 과정도 영향을 줍니다. “DPI가 두 배이니 비용도 두 배”라고 추측하면 안 됩니다.

## 5.10 직접 풀어 보기

1. `markSaved()`를 파일 쓰기 전에 호출하면 어떤 실패에서 잘못된 화면 상태가 생길까요?
2. OCR 도중 하이라이트를 추가했습니다. 기존 결과를 그대로 적용하지 않으려면 무엇을 비교해야 할까요?
3. OCR에서 `worker.cancel()`만 남기고 반복문의 취소 검사를 모두 지우면 무슨 일이 생길 수 있을까요?
4. 8페이지 중 3페이지만 선택했고 실제 새 글자를 찾은 페이지가 1개입니다. 현재 구현은 몇 페이지짜리 PDF를 만들며 어떤 페이지를 교체할까요?

### 해설

1. 디스크 용량 부족이나 권한 오류로 쓰기가 실패해도 UI는 저장됐다고 판단할 수 있습니다. 저장 지점 갱신은 성공 이후여야 합니다.
2. 적어도 시작 시 `revision`과 현재 `revision`이 달라졌는지 확인해야 합니다. 앱은 요청·문서·원본 식별 조건도 함께 확인해 다른 문서나 실행의 결과가 섞이는 것을 막습니다.
3. 취소 표시만 설정되고 계산이 계속될 수 있습니다. 중단 지점을 실제로 확인하는 코드가 필요합니다. 시스템 호출 하나가 끝날 때까지 기다려야 할 수도 있습니다.
4. 문서 전체 8페이지를 유지합니다. 새 인식 결과가 있는 1페이지를 교체하고, 나머지는 원래 페이지를 보존합니다.

### 완료 기준

저장, OCR, 결과 적용 각각에 대해 “시작할 때 검사하는 것”, “끝날 때 다시 검사하는 것”, “실패 시 남아 있어야 하는 것”을 설명해 보세요. 이 세 질문은 이미지 편집기나 노트 앱을 만들 때도 그대로 사용할 수 있습니다.
