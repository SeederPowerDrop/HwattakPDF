# 6장 테스트와 디버깅

## 작은 예제로 시작하기

테스트(test)는 코드에 입력을 주고 **기대한 결과와 실제 결과를 비교하는 일**입니다. 처음부터 큰 앱을 실행할 필요는 없습니다. 다음은 내부 인덱스(index)에 1을 더해 화면에 보일 페이지 번호로 바꾸는 독립 Swift 학습 예제입니다. 실제 앱에서 발췌한 함수는 아닙니다.

```swift
func displayNumber(_ index: Int) -> Int {
    return index + 1
}
let actual = displayNumber(0)
print(actual == 1)
```

출력은 `true`입니다. 함수가 돌려준 실제 값은 1이고, 기대한 값도 1이기 때문입니다. `==`는 두 값이 같은지 검사합니다. 반대로 함수가 실수로 `index + 2`를 반환하면 출력은 `false`가 됩니다. 이것이 실패를 발견한 상태입니다. 테스트가 실패했다고 컴퓨터가 고장 난 것은 아닙니다.

| 준비할 것 | 이 예에서의 값 |
| --- | --- |
| 입력 | 내부 인덱스 `0` |
| 기대한 결과 | 화면 번호 `1` |
| 실제 결과 | 함수를 실행해 얻은 `actual` |

위의 `print`는 눈으로 확인하는 연습입니다. 뒤에서 나오는 `XCTAssertEqual`은 비교 결과가 다르면 테스트 실행기에 실패로 기록하는 도구입니다. “무엇이 나와야 하는가?”를 먼저 정한다는 원리는 같습니다.

**한 번 더 해 보세요.** 입력을 4로 바꾸었다면 기대한 결과도 5로 바꿔야 합니다. 원래 기대값 1을 그대로 두면 올바른 함수도 실패합니다. 테스트의 기대값 역시 사람이 제대로 작성해야 한다는 뜻입니다. 처음에는 1~3절만 읽고 작은 검사 하나를 이해하세요. 파일 충돌과 비동기 테스트는 그다음 단계입니다.

## 이 장에서 배울 것

- 기존 테스트를 준비·실행·확인 세 부분으로 나누어 읽습니다.
- 정상 입력, 경계값(boundary value), 실패 경로, 동작 순서를 구분합니다.
- 순수 함수(pure function)를 검사하는 테스트와 PDF·파일을 함께 사용하는 통합 테스트(integration test)의 차이를 이해합니다.
- 재현 → 원인 좁히기 → 수정 → 회귀 테스트(regression test) → 변경 확인 순서로 작은 수정을 진행합니다.

이 장에서는 저장소에 있는 테스트를 읽습니다. 아래 명령은 독자가 직접 실행해 볼 명령입니다. 테스트 통과 여부는 실행할 때마다 확인해야 하며, 과거에 기록한 검증 결과와 현재 수정한 코드의 검증 결과를 구분해야 합니다.

## 1. 테스트는 무엇을 약속하는가

`3-5`를 입력하면 PDF의 3·4·5쪽을 선택해야 합니다. 다른 앱이 원본 파일을 바꿨다면, 현재 앱에서 편집한 내용으로 그 원본을 알림 없이 덮어써서는 안 됩니다. 이런 기대를 작은 프로그램으로 표현한 것이 테스트입니다. 코드가 바뀐 뒤에도 같은 조건을 다시 확인할 수 있습니다.

테스트도 코드이므로 틀릴 수 있습니다. 좋은 테스트에는 **사용자가 기대하는 결과 또는 지켜야 할 조건**을 직접 적습니다. 테스트에서 현재 구현을 그대로 따라 계산하면 구현의 실수까지 반복할 수 있습니다. 또한 테스트가 통과해도 화면의 자연스러움, 모든 PDF와의 호환성, 성능까지 입증되는 것은 아닙니다.

함수나 작은 구성 요소의 동작을 따로 확인하는 검사를 단위 테스트(unit test), 여러 구성 요소가 함께 작동하는지 확인하는 검사를 통합 테스트라고 합니다. 같은 입력에 같은 결과를 반환하고 외부 상태를 바꾸지 않는 순수 함수는 단위 테스트로 검사하기 좋습니다. 회귀 테스트는 코드를 변경한 뒤 기존에 잘되던 기능이 망가지지 않았는지 확인하는 검사입니다. 회귀 테스트에는 단위 테스트와 통합 테스트를 모두 사용할 수 있습니다.

| 테스트 종류 | 실제 예 | 무엇을 잘 찾는가 |
| --- | --- | --- |
| 작은 로직 검사 | `OCRPageSelection.resolve`에 문자열을 넣기 | 잘못된 입력 처리, 인덱스 변환, 중복·정렬 |
| 상태 전이(state transition) 검사 | `PDFEditHistory`에 편집을 넣고 되돌리기 | 다시 실행할 수 있는 이력, 저장 지점, 실패 후 상태 |
| 문서·파일 통합 검사 | 테스트용 PDF를 열고 회전·저장·외부 교체하기 | 실제 PDFKit과 파일 시스템을 연결할 때 생기는 문제 |
| 화면·입력 검사 | 실제 `PDFView`에 마우스 동작 전달 | 클릭·드래그·포커스 등 입력 경로 |
| 수동 확인 | 앱을 열어 문서 선택·검색·외부 뷰어 확인 | 눈에 보이는 배치, 기기별 조작, 다른 앱과의 호환성 |

## 2. 테스트를 세 부분으로 읽기

[OCRPageSelectionTests.swift](../../Tests/HwattakPDFTests/OCRPageSelectionTests.swift)의 `testCompactDescriptionIsCanonicalAndRoundTrips`는 페이지 목록의 표기와 변환 결과를 검사합니다. 아래는 기존 테스트에서 준비·실행·확인 구간을 표시한 발췌입니다.

```swift
// 준비(Arrange): 중복과 불규칙한 순서가 있는 입력
let indexes = [10, 2, 3, 4, 0, 7, 8, 8]

// 실행(Act): 사람이 편집할 수 있는 페이지 목록으로 변환
let description = OCRPageSelection.compactDescription(indexes)

// 확인(Assert): 원하는 표기와 왕복 결과를 각각 확인
XCTAssertEqual(description, "1, 3-5, 8-9, 11")
XCTAssertEqual(try resolve(.custom, description), Array(Set(indexes)).sorted())
```

`XCTAssertEqual`은 두 값이 같은지 확인하는 단언(assertion)입니다. 단언은 반드시 성립해야 할 조건을 코드로 표현한 것입니다. 첫 번째 확인에서는 구체적인 정답 문자열을 제시합니다. 두 번째 확인에서는 문자열로 바꿨다가 다시 읽어도 원래 의미를 유지해야 한다는 **왕복 성질**(round-trip property)을 검사합니다. 왕복 성질만 검사하면 두 함수가 같은 실수를 할 때 문제를 놓칠 수 있으므로, 구체적인 정답도 함께 확인하는 것이 좋습니다.

여기서 `resolve`는 테스트 파일 끝에 있는 짧은 도우미 함수(helper function)입니다. 실제 앱의 `OCRPageSelection.resolve`를 호출하며 기본 문서 길이를 12쪽으로 지정합니다. 테스트를 읽다가 모르는 함수가 나오면 앱의 기능을 구현한 함수인지, 반복되는 준비 코드를 줄이기 위한 테스트 도우미인지부터 확인해 보세요.

| 표현 | 읽는 방법 |
| --- | --- |
| `XCTAssertEqual(a, b)` | 결괏값이 기댓값과 같은지 확인합니다. |
| `XCTAssertTrue(condition)` | 지켜야 할 조건이 참인지 확인합니다. |
| `XCTAssertFalse(condition)` | 조건이 거짓인지 확인합니다. |
| `XCTAssertNil(value)` | 결과가 `nil`인지 확인합니다. |
| `XCTAssertThrowsError(try operation())` | 연산에서 오류가 발생하는지 확인합니다. |
| `try XCTUnwrap(optional)` | 이후 검사에 필요한 값을 꺼냅니다. 값이 없으면 테스트 실패로 기록합니다. |

`@testable import HwattakPDF`는 테스트가 앱 모듈(module)의 내부 선언에 접근할 수 있게 하는 표시입니다. `@MainActor`가 붙은 테스트는 앱 상태와 PDFKit 연산이 요구하는 메인 액터(main actor)에서 실행됩니다. `throws`가 붙은 테스트는 준비나 실행 중 발생한 오류를 테스트 실패로 전달할 수 있습니다.

## 3. 경계값: 허용 범위의 양끝과 그 바깥을 검사하기

[OCRPageSelection.swift](../../Sources/HwattakPDF/Models/OCRPageSelection.swift)는 사람에게 보이는 번호를 0부터 시작하는 인덱스(index)로 변환합니다. 첫 페이지 번호인 `1`, 마지막 페이지 번호, 그리고 허용 범위를 한 칸 벗어난 값에서 오류가 생기기 쉽습니다. 이런 범위의 경계에 있는 값들을 검사하는 것이 경계값 테스트입니다.

| 입력·조건 | 기대 결과 | 대응하는 기존 검사 |
| --- | --- | --- |
| 전체 범위, 164쪽 | `nil` — 전체라는 내부 약속 | `testAllAndCurrentPageScopesUseOriginalIndexes` |
| 현재 인덱스 50, 164쪽 | `[50]` — 이미 내부 인덱스 | 같은 검사 |
| 현재 인덱스 -1 또는 164 | 오류 | 같은 검사 |
| `2-2, 2` | `[1]` | `testCustomSelectionNormalizesRangesWhitespaceAndDuplicates` |
| 빈 문자열, `1,,2`, `3-1`, `1.5` | 오류 | `testEmptyMalformedAndReversedInputsAreRejected` |
| 12쪽 문서에 `0`, `13`, `1-13` | 오류 | `testOutOfRangeAndOverflowCannotExpandInvalidRanges` |
| 정수 범위를 넘는 아주 긴 숫자 | 오류, 거대한 범위 생성 금지 | 같은 검사 |

마지막 줄의 검사가 필요한 이유도 생각해 보세요. 잘못된 범위의 숫자를 먼저 모두 만든 뒤 유효한 번호만 고르면 메모리를 지나치게 많이 쓰거나 정수 오버플로(overflow)가 발생할 수 있습니다. 앱 코드는 양끝을 먼저 검증한 뒤 `first...last`를 순회합니다. 테스트는 결과의 정확성과 함께, 잘못된 요청을 **자원이 많이 드는 작업 전에 거절한다**는 설계도 확인합니다.

현재 `XCTAssertThrowsError`를 사용하는 테스트 중 일부는 오류가 발생하는지만 검사합니다. 사용자에게 형식 오류와 범위 오류를 구분해 안내해야 한다면, 전달된 오류를 `OCRPageSelectionError`의 해당 사례와 비교하는 검사를 추가할 수 있습니다. 검증한 범위만 정확하게 설명하는 습관을 익혀 보세요.

## 4. 상태를 가진 기능의 동작 순서 검사하기

이 앱의 페이지 범위 파서(parser)는 같은 입력에 같은 출력을 돌려주지만, 실행 취소의 결과는 **이전에 어떤 일을 했는지**에 따라 달라집니다. 파서는 입력 문자열을 규칙에 따라 해석하는 코드입니다. [PDFEditHistoryTests.swift](../../Tests/HwattakPDFTests/PDFEditHistoryTests.swift)는 개별 명령의 동작과 여러 명령의 실행 순서를 모두 검사합니다.

### 4.1 한도를 넘긴 뒤 얼마나 되돌릴 수 있는가

`testHistoryKeepsOnlyLatestTwentyTwoCommandsAndSupportsRedo`는 정수 `value`를 0에서 25까지 바꾸면서 각 변경을 등록합니다. 문서를 만들지 않고도 실행 취소 구조를 검사할 수 있는 작은 모형입니다.

```text
0 → 1 → … → 25                 25번 편집
보관 명령: 최근 22개            첫 3개 명령은 이력에서 제거
22번 undo 후 값: 3              문서 상태의 오래된 편집은 그대로 남음
22번 redo 후 값: 25             보관한 변경을 다시 실행
```

오래된 이력을 버려도 해당 편집이 문서에 적용된 결과는 남습니다. 결과 `3`을 확인하는 이유가 바로 이것입니다. `PDFEditHistory.register`는 이미 실행한 편집을 기록합니다. 테스트에서도 먼저 `value = nextValue`를 수행하고, 실행 취소(undo)와 다시 실행(redo)에 사용할 클로저(closure)를 등록합니다. 클로저는 나중에 실행할 코드와 그 코드에서 사용할 주변 값을 함께 묶어 전달할 수 있는 문법입니다.

### 4.2 실행 취소를 했다고 미저장 변경이 없어지는 것은 아니다

`testSavedCheckpointTracksUndoAndRedoPosition`은 실제 PDF를 사용합니다.

| 동작 | 회전 | 미저장 변경 `isDirty` |
| --- | --- | --- |
| 문서 열기 | 0° | 없음 |
| 회전 | 90° | 있음 |
| 저장 | 90° | 없음 |
| 실행 취소 | 0° | 있음 — 디스크는 90° |
| 다시 실행 | 90° | 없음 — 저장 지점과 같음 |

`PDFEditHistory`는 현재 상태와 저장한 상태의 범용 고유 식별자(UUID, universally unique identifier)를 비교합니다. 여기서 UUID는 이력의 위치를 식별하는 값입니다. PDF 내용으로 계산한 해시(hash)와는 용도가 다릅니다. UUID를 비교하면 저장할 때의 상태로 돌아왔는지 정확히 확인할 수 있습니다.

### 4.3 실패가 발생하면 무엇을 유지해야 하는가

`testFailedCommandDoesNotMoveHistoryStacksOrSavedToken`은 실행 취소용 클로저가 즉시 오류를 던지도록 만듭니다. 오류가 발생했을 때 실행 취소 명령은 사라지거나 다시 실행 목록으로 옮겨져서는 안 됩니다. 저장 지점도 그대로 유지해야 합니다.

앱 코드는 `try command.undoMutation()`이 성공한 다음에 스택(stack)과 상태 ID를 바꿉니다. `defer`는 실행에 실패해도 `isApplyingCommand`를 원래대로 복구합니다. 다만 이력을 관리하는 클래스가 클로저 안에서 이미 일어난 일부 변경까지 자동으로 되돌리지는 않습니다. 실패했을 때 이력이 유지되는지 확인하는 것과 문서 연산의 실패 원자성(failure atomicity)을 확인하는 것은 서로 다른 검사입니다. 실패 원자성은 연산에 실패하면 일부 변경만 남지 않고 시작 전 상태를 유지하는 성질입니다.

같은 파일의 `testPenThenPageDeleteUsesExactPageAndAnnotationIdentity`는 페이지를 지웠다가 되돌려도 같은 페이지·주석 객체를 사용하는지 `===`로 확인합니다. `==`는 값이 같은지, `===`는 같은 참조 객체인지 확인합니다. 서로 다른 주석을 잘못 연결하는 버그(bug)를 찾으려면 이 차이를 이해해야 합니다.

## 5. 파일 저장 테스트: 앱 안팎의 작업을 함께 보존하기

[PDFExternalModificationConflictTests.swift](../../Tests/HwattakPDFTests/PDFExternalModificationConflictTests.swift)의 `testExternalAtomicReplacementBlocksOverwriteAndPreservesBothVersions`를 읽어 보세요.

1. **준비:** 임시 폴더에 테스트용 1페이지 PDF를 만들고 앱의 문서 모델에서 엽니다.
2. **앱의 편집:** 열린 문서를 90° 회전합니다. 아직 원본에는 저장하지 않습니다.
3. **외부 변경 재현:** 다른 앱의 동작을 흉내 내어 원본을 2페이지 PDF로 교체합니다.
4. **실행:** 앱에서 원본에 저장을 시도합니다.
5. **확인:** 저장은 실패하고 메모리의 편집 내용은 미저장 상태(dirty state)로 남습니다. 외부에서 바꾼 파일의 바이트와 2페이지 구조도 그대로 유지됩니다.

이 테스트가 기대하는 결과는 **저장을 거부하면서 두 버전을 보존하는 것**입니다. 파일 크기나 수정일을 확인하는 데 그치지 않고, 외부 파일의 `Data`를 저장 시도 전후에 비교하여 실제 내용도 보존되었는지 검사합니다.

이어서 `testSaveAsRemainsARecoveryPathAfterOriginalChangedExternally`는 별도 파일로 저장할 수 있는지, 그 사본의 회전이 90°인지, 외부에서 바꾼 원본의 바이트가 그대로인지 확인합니다. 충돌을 감지한 뒤에도 사용자가 편집 내용을 보존할 방법이 있는지까지 검사하는 것입니다.

테스트 PDF는 코드로 만든 작은 문서입니다. 이렇게 검사를 위해 준비한 입력이나 환경을 **테스트 픽스처**(test fixture)라고 합니다. 임시 폴더를 사용하고 `addTeardownBlock`을 등록하여 테스트가 끝난 뒤 정리합니다. 실제 사용자의 교재나 개인 문서 없이도 페이지 수·회전·파일 교체 등 필요한 조건을 재현할 수 있습니다.

## 6. 비동기 테스트: ‘기다리면 되겠지’를 줄이기

OCR은 즉시 끝나지 않습니다. 취소를 누르는 시점과 인식기가 결과를 반환하는 시점이 겹칠 수 있습니다. 이처럼 작업이 진행되는 순서에 따라 결과가 달라질 수 있는 상황을 경쟁 상태(race condition)라고 합니다. `testCancellationAfterRecognizerReturnsStillCleansUpAndAllowsRestart`는 테스트용 인식기와 게이트(gate)를 사용하여 “시작됨 → 취소 → 반환”의 순서를 만듭니다. 게이트는 테스트 코드가 특정 지점에서 작업을 잠시 멈췄다가 다시 진행시킬 수 있도록 하는 장치입니다.

그다음 작업 상태가 대기 상태인 `.idle`로 돌아오고 새 OCR을 시작할 수 있는지 검사합니다. 취소 문구를 표시했는지뿐 아니라 실제로 다음 작업을 진행할 수 있는지도 확인하는 것입니다. 정리가 덜 되어 이전 비동기 작업(task)이 남으면 새 작업이 막힐 수 있기 때문입니다.

완료 상태를 확인하는 도우미는 짧은 간격으로 상태를 확인하되 반복 횟수를 제한합니다. 항상 일정한 시간만 기다리면 빠른 Mac에서는 시간을 낭비하고, 느린 환경에서는 기다리는 시간이 부족할 수 있습니다. 가능한 경우에는 시간에 의존하지 않고 작업 시작 신호, 명시적인 완료 알림, 제어할 수 있는 입력을 기준으로 검사합니다.

## 7. 직접 실행하는 순서

macOS와 Swift 개발 도구가 설치된 환경에서 프로젝트 폴더를 터미널(terminal)로 열어 보세요. 이 앱은 AppKit·PDFKit을 사용하므로 알고리즘만 검사하는 테스트를 골라도 앱 타깃(target)을 빌드(build)하는 데 Mac 환경이 필요합니다. 타깃은 함께 빌드할 소스와 설정의 묶음이며, 빌드는 소스 코드에서 실행 가능한 결과물을 만드는 과정입니다.

처음에는 가장 작은 테스트 하나를 골라 실행해 보세요.

```sh
swift test --filter OCRPageSelectionTests/testCustomSelectionNormalizesRangesWhitespaceAndDuplicates
```

관련 테스트 클래스 전체를 확인하려면 다음 명령을 각각 실행해 보세요.

```sh
swift test --filter OCRPageSelectionTests
swift test --filter PDFEditHistoryTests
swift test --filter PDFExternalModificationConflictTests
```

필터를 잘못 지정하면 테스트가 하나도 실행되지 않을 수 있습니다. 종료 코드(exit code)와 함께 **실제로 실행한 검사 이름·개수, 실패, 제외된 검사**를 확인해 보세요. `swift test`는 빌드 실패도 보고하므로, 먼저 코드의 컴파일(compile)이 실패했는지, 실행된 검사의 결과가 기댓값과 달랐는지 구분해야 합니다.

전체 검사는 저장소에 있는 배치 실행기(batch runner)를 사용합니다. 여러 테스트를 묶음으로 나누어 실행하는 스크립트입니다.

```sh
./scripts/run_test_batches.sh
```

[실행기](../../scripts/run_test_batches.sh)는 테스트 클래스의 누락·중복을 검사한 뒤 일곱 묶음을 별도 프로세스(process)로 실행합니다. 프로세스는 운영체제가 실행 중인 프로그램을 관리하는 단위입니다. 실제 `PDFView` 입력과 양식 편집 테스트는 AppKit/PDFKit에서 프로세스 전체가 공유하는 상태가 뒤의 검사에 영향을 줄 수 있어 분리했습니다. 실행기는 임시 빌드 파일과 캐시(cache)를 작업 폴더 안에 만들며 SwiftPM의 `--disable-sandbox` 옵션을 포함합니다. 이는 개발 도구의 실행 환경을 설정하는 옵션이며, PDF 앱의 모든 보안 경계를 해제하지는 않습니다. 실행 환경에서 접근을 차단하면 실패 기록을 남기고 필요한 권한을 확인해 해결합니다.

번역 키·리소스 등의 구조를 확인하는 [정적 검사(static check)](../../scripts/validate_project.sh)도 별도로 실행합니다. 정적 검사는 앱을 실행하지 않고 소스나 파일의 구조를 확인하는 검사입니다.

```sh
./scripts/validate_project.sh
```

짧은 주석이나 설명을 바꾼 뒤에는 우선 변경 내용과 관련 검사를 확인합니다. 이미 통과한 검사를 새로운 이유 없이 계속 반복할 필요는 없습니다. 실행하지 않은 검사는 “실행 안 함”, 환경 때문에 제외된 검사는 “제외됨”으로 기록합니다.

## 8. 버그를 공부하는 방법

“OCR이 안 된다”라는 설명을 더 구체적인 관찰로 바꿔 보세요. 인식이 시작되지 않았는지, 완료했는데 새 글자가 없는지, 결과를 적용하지 않았는지, 저장 파일을 다시 열어 확인하지 않았는지 구분해 봅니다. 각 질문에 따라 살펴볼 코드가 달라집니다.

1. **재현 기록:** 앱·macOS 버전, 문서 페이지 수, 동작 순서, 기대 결과와 실제 결과를 적어 보세요.
2. **작게 줄이기:** 코드로 만든 한 페이지 문서나 필요한 페이지만으로 문제가 재현되는지 확인해 보세요.
3. **처리 단계 따라가기:** 화면 입력 → 상태를 바꾸는 메서드 → 서비스의 처리 결과 → 저장 파일 중 어느 단계까지 올바른지 확인해 보세요.
4. **원인을 설명할 검사:** 잘못된 동작을 구체적으로 확인하는 테스트를 찾거나 추가해 보세요. 모든 문제에 사용자 인터페이스(user interface, UI) 테스트가 필요한 것은 아닙니다.
5. **최소 수정·관련 재검사:** 원인이 있는 부분을 고친 뒤, 그 부분과 연결된 기존 기능도 확인해 보세요.
6. **변경 사항(diff) 검토:** 의도한 변경만 있는지, 사용자가 하던 작업을 덮어쓰지 않았는지 확인해 보세요.

예를 들어 [OCR 오류 기록](../OCR-TEXT-REPAIR-2026-09-25.md)에서는 화면의 ‘췌장’과 PDF에서 추출한 텍스트를 비교하여 검색 알고리즘의 문제와 OCR 인식 결과의 문제를 구분했습니다. 이처럼 어느 단계에서 처음 값이 잘못되는지 찾아 오류의 원인을 밝히고 수정하는 과정을 디버깅(debugging)이라고 합니다.

Git의 `diff`는 비교 기준과 현재 파일 사이의 차이를 보여 줍니다. `+`는 추가한 줄, `-`는 제거한 줄을 나타냅니다. Git에 아직 등록되지 않은 새 파일은 기본 `git diff`에 본문이 나오지 않으므로 `git status`와 함께 확인합니다.

```sh
git status --short
git diff -- Sources/HwattakPDF/Models/PDFEditHistory.swift
git diff --check
```

`git diff --check`는 공백 오류 등 텍스트의 문제를 찾으며, 프로그램의 동작까지 검증하지는 않습니다. 코드 주석을 바꿨다면 실행 코드도 함께 바뀌지는 않았는지 특히 살펴보세요. 디버거(debugger)를 사용할 때는 `resolve`의 입력과 반환값, `undo` 전후의 스택 원소 수, 저장 직전의 원본 파일 버전(source version)처럼 **가설을 구분하는 데 도움이 되는 값**을 확인할 수 있는 코드 위치에 중단점(breakpoint)을 설정합니다. 중단점은 실행을 잠시 멈추고 상태를 살펴볼 위치입니다. 외부 API 키나 실제 문서 전체를 실행 기록에 남길 필요는 없습니다.

## 9. 연습과 해설

### 연습 1 — 아직 빠진 확인은 무엇일까

테스트가 `XCTAssertThrowsError(try resolve(.custom, "13"))`만 검사합니다. 기본 문서 길이가 12쪽일 때 “범위 초과”라는 안내까지 올바르다고 말할 수 있을지 생각해 보세요.

**해설:** 오류가 발생한다는 점만 확인했고, 어떤 오류인지는 아직 확인하지 않았습니다. 요구 사항에 안내의 구분까지 포함된다면, 오류를 전달받는 클로저에서 `OCRPageSelectionError.outOfBounds(pageCount: 12)`와 비교해야 합니다. 테스트가 보장한다고 설명하는 범위는 실제 단언으로 확인한 범위를 넘지 않아야 합니다.

### 연습 2 — 실행 취소의 결과를 예상하기

편집 A → 편집 B → B 실행 취소 → 새 편집 C 순서로 조작했습니다. B를 다시 실행할 수 있어야 하는지 생각해 보고, 기존 테스트에서 근거를 찾아보세요.

**해설:** 현재 앱은 편집 이력을 한 줄로 관리하므로 새 편집 C를 등록할 때 다시 실행 목록을 비웁니다. `testNewEditClearsRedoAndRetainedPageBudgetTrimsOldestCommands`의 `branch` 등록 부분에서 이 동작을 확인합니다. 편집 B와 새 편집 C로 갈라진 두 경로를 모두 보관하려면 별도의 분기 이력 설계가 필요합니다.

### 연습 3 — 저장 실패를 확인하는 세 조건

다른 앱이 원본을 교체한 뒤 저장을 눌렀습니다. 오류 메시지를 검사하는 것 외에 꼭 확인할 세 가지를 적어 보세요.

**해설:** 외부에서 바꾼 원본 파일의 바이트가 보존되는지, 앱 안의 편집 내용이 미저장 상태로 유지되는지, 다른 이름으로 사본을 저장하여 편집을 보존할 수 있는지 확인합니다. 앞에서 살펴본 충돌 차단 테스트와 별도 저장 테스트가 이 조건들을 나누어 검사합니다. 실패했을 때 데이터를 보존하고 이후에도 작업을 이어 갈 수 있도록 하는 것까지 사용자 경험에 포함됩니다.

## 학습 기록에 남길 문장

“페이지 범위 파서에서 정상 범위와 잘못된 입력을 확인했습니다. 관련 테스트 N개를 실행했고 실패는 X개, 제외는 Y개였습니다. 실제 앱의 OCR 화면과 외부 PDF 뷰어와의 호환성은 이번에 확인하지 않았습니다.”

이 문장의 숫자는 직접 실행한 결과로 채워 보세요. 확인한 것과 아직 확인하지 않은 것을 구분해 설명하는 것은 유지보수에 필요한 중요한 습관입니다.
