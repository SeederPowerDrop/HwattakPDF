# HwattakPDF로 배우는 앱 개발과 Rust

우리가 만든 Mac PDF 앱을 교재로 삼아, 화면에서 시작한 동작이 데이터와 파일로 이어지는 과정을 배웁니다. 코드를 처음 공부하거나 문법을 조금 아는 독자를 위한 과정입니다. 목표는 모든 줄을 외우는 것이 아니라 **어떤 코드가 어떤 문제를 해결하는지 설명하고, 작은 변경을 스스로 검사하는 것**입니다.

**코드를 한 번도 작성하지 않았다면 [0장](00-FIRST-STEPS.md)부터 읽으세요.** 숫자에 이름 붙이기, 조건에 따라 동작 고르기, 함수를 호출하기부터 시작합니다. 첫 목표는 PDF 앱 전체를 이해하는 것이 아니라, “현재 페이지가 1에서 2로 바뀌는 짧은 코드”를 자신의 말로 설명하는 것입니다.

현재 앱은 **Swift**로 작성했으며, 화면과 PDF·글자 인식 기능에 **SwiftUI·AppKit·PDFKit·Vision**을 사용합니다. Rust는 별도로 실행할 수 있는 예제로 학습합니다. 같은 페이지 선택 문제를 두 언어로 읽으면 Swift의 값(value)·참조(reference)·오류 처리(error handling)와 Rust의 소유권(ownership)·차용(borrowing)·`Result`를 비교할 수 있습니다.

교재는 2026-09-30에 작성했으며, 2026-10-01 소스 통합에 포함한 HwattakPDF 0.9.0 build 20의 코드(source code)를 기준으로 합니다. 최근 OCR 수정과 학습 예제를 함께 저장소에 기록했습니다. Git의 커밋(commit)은 변경 사항을 버전 관리 기록으로 남기는 작업입니다. 이 교재는 소스의 구조와 동작을 설명하며, 설치된 앱이나 공개 배포본의 검증 결과는 별도로 확인해야 합니다.

## 용어를 읽는 방법

전문 용어는 각 장에서 처음 설명할 때 **한국어**(English) 형태로 원어를 함께 적습니다. 예를 들어 차용(borrowing), 의존성 주입(dependency injection), 강제 언래핑(forced unwrapping)처럼 표기합니다. 한국어로 낯설게 번역하기보다 원어의 발음을 그대로 쓰는 용어도 클로저(closure), 트레이트(trait)처럼 함께 적습니다.

같은 장에서 반복할 때는 한국어를 중심으로 씁니다. `Result`, `@StateObject`, `Task.detached` 같은 실제 코드 이름은 그대로 두므로, 편집기에서 검색하거나 공식 문서와 대조할 수 있습니다. 약어는 주요 설명에서 전체 이름을 함께 적고, 뒤의 용어 표에서는 자주 찾는 개념을 다시 확인할 수 있습니다.

## 첫 공부는 이렇게 시작하기

첫날에는 0장의 변수·대입·조건문까지만 읽어도 충분합니다. 짧은 코드를 보고 줄마다 어떤 값이 남는지 종이에 써 보세요. 개발 도구가 준비되지 않았어도 시작할 수 있습니다. 실행해 볼 준비가 되면 [Swift 첫 실습](../../Examples/Learning/SwiftFirstSteps/README.md)을 사용하세요. 한 파일짜리 예제이므로 현재 앱이나 개인 PDF를 수정하지 않습니다.

다음에는 1장에서 앱의 역할을 훑고, 2장에서 페이지 이동 함수 하나를 읽습니다. 그 뒤 4장의 입력 `2, 4`를 내부 값 `[1, 3]`으로 바꾸는 연습으로 이어 가세요. `1, 3-5, 8` 같은 범위 입력은 단일 번호가 이해된 다음에 읽습니다. 처음부터 가장 큰 `PDFWorkspaceState.swift`를 끝까지 읽을 필요는 없습니다.

각 장의 **처음 읽는 순서**나 **작은 예제로 시작하기**는 먼저 읽을 부분입니다. 심화 설명은 두 번째 독서에서 확인해도 됩니다. 모르는 용어가 나왔다고 앞의 모든 내용을 이해하지 못한 것은 아닙니다. 우선 그 코드가 받는 값과 돌려주는 결과를 찾으세요.

### 처음 세 번의 공부

| 공부할 때 | 할 일 | 이해했는지 확인하는 질문 |
| --- | --- | --- |
| 첫 번째 | 0장에서 변수와 조건문을 읽고 값을 적기 | `page = page + 1` 뒤에 값이 얼마인가요? |
| 두 번째 | 0장의 함수·배열, Swift 첫 실습 읽기 | 5쪽 문서에서 6쪽을 요청하면 왜 그대로 머무르나요? |
| 세 번째 | 2장 페이지 이동, 4장 번호 변환 읽기 | 사용자에게 보이는 3쪽은 왜 내부에서 2인가요? |

한 번에 20~30분씩 나누어 읽어도 됩니다. 다음 단계로 넘어갈 기준은 페이지 수가 아니라, 예제의 결과를 실행 전에 예상할 수 있는지입니다. Rust는 7장 첫 실습에서 같은 규칙을 다시 표현해 본 뒤 소유권 설명으로 넘어갑니다.

한 번 공부할 때 다음 순서를 반복합니다.

1. **예측:** 입력을 하나 정하고 결과를 먼저 적습니다.
2. **읽기:** 코드의 입력, 검사, 상태 변경, 결과 네 부분을 표시합니다.
3. **실행:** 관련 테스트나 독립 예제를 실행해 예측과 비교합니다.
4. **설명:** 왜 그 순서여야 하는지 자신의 말로 두세 문장 적습니다.
5. **확장:** 경계값 하나만 바꿔 다시 예측합니다.

이 책의 PDF를 HwattakPDF에 열고, 코드 편집기는 나란히 두면 좋습니다. PDF에서는 `guard`, `revision`, `소유권` 같은 단어를 검색하고 이해되지 않은 곳에 메모하세요. 알고리즘 실습에는 실제 개인 문서가 필요하지 않습니다.

## 자주 만나는 용어

이 표는 모르는 말이 나왔을 때 찾아보는 사전입니다. 처음부터 외울 필요는 없습니다. 지금은 0장에서 값·변수·함수를 먼저 익히고, 나머지는 해당 장에서 예제와 함께 읽으세요.

| 용어 | 이 앱에서의 뜻 |
| --- | --- |
| 상태(state) | 현재 페이지, 선택, 저장 여부처럼 프로그램이 현재 기억하는 값 |
| 타입(type) | 값의 종류와 그 값에 허용되는 연산을 정하는 기준 |
| 소유권(ownership) | 값이나 자원을 누가 보유하고 수명을 책임지는지 정하는 규칙 |
| 차용(borrowing) | Rust에서 소유권을 넘겨받지 않고 참조로 값을 사용하는 방식 |
| 이동(move) | Rust에서 값의 소유권을 다른 변수나 함수로 넘기는 일 |
| 수명(lifetime) | 참조가 유효하게 사용될 수 있는 범위 |
| 불변 조건(invariant) | 작업 전후에 항상 지켜야 하는 조건 |
| 인덱스(index) | 이 앱에서는 0부터 시작하는 배열 원소의 위치 |
| 파싱(parsing) | 입력의 구조를 분석해 프로그램에서 다룰 값으로 바꾸는 일 |
| 스택(stack) | 마지막에 넣은 항목을 먼저 꺼내는 자료구조 |
| 직렬화(serialization) | 메모리 데이터를 파일이나 전송 형식으로 바꾸는 일 |
| 스냅샷(snapshot) | 특정 시점의 데이터를 고정해 둔 사본 |
| 참조(reference) | 다른 곳에 있는 값이나 객체를 가리키는 연결 |
| 클로저(closure) | 실행할 코드와 그 코드가 사용하는 주변 값을 함께 다루는 기능 |
| 캡처(capture) | 클로저가 주변 문맥의 값을 사용하도록 보관하거나 참조하는 일 |
| 옵셔널(optional) | Swift에서 값이 있을 수도, 없을 수도 있음을 나타내는 타입 |
| 트레이트(trait) | Rust에서 타입이 제공할 동작을 선언하는 언어 기능 |
| 패턴 매칭(pattern matching) | 값의 형태를 구분하고 그 안의 값을 꺼내 처리하는 방식 |
| 비동기 작업(asynchronous task) | 실행 도중 기다림이 필요하면 양보했다가 이어갈 수 있는 작업 |
| 협력적 취소(cooperative cancellation) | 작업 코드가 취소 요청을 확인하고 스스로 중단하는 방식 |
| 미저장 상태(dirty state) | 현재 편집 상태가 마지막으로 저장한 상태와 다른 상태 |
| 저장 상태와 일치하는 상태(clean state) | 현재 편집 상태가 마지막으로 저장한 상태와 같은 상태 |
| 리비전(revision) | 결과가 문서의 어느 변경 단계에 속하는지 구분하는 값 |
| 지문(fingerprint) | 입력 문서나 설정이 같은지 확인하기 위해 내용으로부터 계산한 식별 값 |
| 체크포인트(checkpoint) | 완료된 작업을 재사용할 수 있도록 중간 결과를 남긴 기록 |
| 회귀(regression) | 변경으로 인해 이전에 되던 동작이 다시 잘못되는 현상 |
| 테스트 픽스처(test fixture) | 테스트에 쓰도록 준비한 데이터나 객체·환경 |
| 의존성 주입(dependency injection) | 필요한 구성 요소를 내부에서 고정하지 않고 외부에서 전달하는 설계 방식 |

## 학습 기록 양식

다음 다섯 줄을 매번 짧게 채워 보세요. 정답을 외우는 것보다 결과가 생긴 이유를 설명하는 연습입니다.

```text
오늘 읽은 함수:
내가 예상한 입력과 결과:
실제로 확인한 결과:
그 순서나 자료구조가 필요한 이유:
```
